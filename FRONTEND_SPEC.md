# FRONTEND_SPEC.md

## 1. Назначение документа

Этот документ описывает фронтенд AI-редактора новостных статей: структуру интерфейса, экраны, компоненты, состояния, мобильную адаптацию, UX-логику и требования к взаимодействию с backend.

Документ предназначен для Codex и должен использоваться вместе с:

- `README.md`
- `PROJECT_BRIEF.md`
- `PRODUCT_REQUIREMENTS.md`
- `USER_FLOWS.md`
- `ARCHITECTURE.md`
- `DATABASE_SCHEMA.md`
- `API_CONTRACTS.md`
- `PROMPTING_SPEC.md`
- `ADMIN_PANEL.md`

## 2. Общая идея интерфейса

Интерфейс должен быть похож на ChatGPT, но адаптирован под создание новостных статей.

Основная рабочая область:

1. Список диалогов.
2. Центральная область чата.
3. Сообщения пользователя и ИИ.
4. Над полем ввода — параметры генерации статьи.
5. Внизу — поле ввода сырого материала, кнопка загрузки `.docx` и кнопка отправки.

Интерфейс должен быть простым, быстрым и удобным на мобильных устройствах.

## 3. Технологический подход

Для MVP использовать серверный frontend внутри FastAPI-приложения:

- Jinja2 templates;
- HTML;
- CSS;
- vanilla JavaScript;
- опционально HTMX для частичного обновления интерфейса;
- опционально Alpine.js для небольших интерактивных состояний.

Не использовать React/Vue/Svelte в первой версии, чтобы не усложнять сборку и развёртывание.

Проект должен оставаться одним Python-приложением, разворачиваемым на VPS через `venv`.

## 4. Основные принципы UI/UX

### 4.1. Приоритеты

1. Мобильный интерфейс в первую очередь.
2. Минимум лишних экранов.
3. Быстрый доступ к созданию статьи.
4. Ясные состояния: ожидание, генерация, очередь, ошибка, готово.
5. Пользователь не должен терять введённый материал при ошибке модели.
6. Все действия должны быть понятны PR-специалисту без технических знаний.

### 4.2. Язык интерфейса

Весь интерфейс — на русском языке.

Тон интерфейсных сообщений — спокойный, деловой, без технического жаргона.

Пример:

- хорошо: `ИИ готовит материал...`
- плохо: `Generation job is running`

### 4.3. Цвета и стиль

Специальный брендбук отсутствует. Использовать нейтральный современный стиль:

- светлый фон;
- тёмный основной текст;
- мягкие серые границы;
- один акцентный цвет для кнопок;
- карточки с лёгким скруглением;
- достаточные отступы;
- читаемая типографика.

Тёмная тема в первой версии не нужна.

## 5. Роли интерфейса

В приложении есть две роли:

1. `user` — обычный пользователь.
2. `admin` — администратор.

### 5.1. Обычный пользователь может

- войти в систему;
- видеть только свои диалоги;
- создать новый диалог;
- ввести сырой материал вручную;
- загрузить `.docx`;
- выбрать параметры генерации;
- отправить материал в модель;
- получить заголовки, лид, статью и вопросы при необходимости;
- продолжить общение с ИИ для доработки статьи;
- скопировать ответ;
- скачать готовый материал в `.txt`;
- откатиться к предыдущей версии статьи, если версия существует.

### 5.2. Администратор может

- войти в систему;
- управлять пользователями;
- создавать пользователей;
- блокировать пользователей;
- менять пароли пользователей;
- видеть все диалоги всех пользователей с указанием владельца;
- просматривать технические логи генераций;
- редактировать мастер-промт;
- менять системные настройки;
- видеть debug-промпт, который был отправлен в модель.

## 6. Основные экраны

## 6.1. Экран входа

URL: `/login`

### Назначение

Позволяет пользователю или администратору войти в систему.

### Поля

- `Логин`
- `Пароль`

### Кнопки

- `Войти`

### Особенности

- Самостоятельной регистрации нет.
- Пользователей создаёт только администратор.
- Если логин или пароль неверные, показать ошибку: `Неверный логин или пароль`.
- Если пользователь заблокирован, показать ошибку: `Аккаунт заблокирован. Обратитесь к администратору`.

### Требования к UX

- Поля должны быть крупными и удобными для мобильного ввода.
- Пароль должен иметь стандартный тип `password`.
- После успешного входа:
  - обычный пользователь попадает на `/app`;
  - администратор может попасть на `/app` или `/admin`, в зависимости от реализации.

## 7. Header

Header должен быть простым.

### Для обычного пользователя

Содержит:

- название продукта, например `AI-редактор статей`;
- кнопку открытия списка диалогов на мобильном;
- логин пользователя;
- кнопку `Выйти`.

### Для администратора

Дополнительно:

- ссылка `Админка`.

## 8. Sidebar: список диалогов

### Назначение

Позволяет пользователю видеть историю своих диалогов и создавать новые.

### Элементы

- кнопка `+ Новый диалог`;
- список диалогов;
- дата последнего обновления диалога;
- визуальное выделение активного диалога.

### Требования

- В первой версии не нужны переименование и удаление диалогов.
- Название диалога задаётся пользователем при создании.
- Если диалогов нет, показать пустое состояние:

```text
Диалогов пока нет.
Создайте первый диалог, чтобы подготовить статью.
```

## 9. Создание нового диалога

При нажатии `+ Новый диалог` показать форму.

### Поля

- `Название диалога` — обязательное.

### Кнопки

- `Создать`
- `Отмена`

### Валидация

- Поле не может быть пустым.
- Рекомендуемый максимум: 120 символов.

### Поведение

После создания пользователь попадает в пустой чат этого диалога.

## 10. Область сообщений

### Типы сообщений

1. Сообщение пользователя.
2. Сообщение ИИ.
3. Системное состояние генерации.
4. Ошибка.

### Сообщение пользователя

Содержит:

- сырой материал или инструкцию по доработке;
- при необходимости отметку, что текст был загружен из `.docx`;
- дату/время отправки можно не показывать в MVP.

### Сообщение ИИ

Содержит результат генерации или доработки.

Для первичной генерации структура ответа должна быть визуально читаемой:

```text
Варианты заголовков
1. ...
2. ...
3. ...

Лид
...

Статья
...

Вопросы к пользователю
...
```

Если вопросов нет, блок вопросов можно не показывать.

### Кнопки у сообщения ИИ

У каждого полного ответа ИИ:

- `Копировать`
- `Скачать TXT`

Если есть предыдущая версия статьи:

- `Откатиться к предыдущей версии`

### Подсказка про память ИИ

После первой генерации в чате должна быть видимая подсказка:

```text
ИИ помнит только последнюю версию статьи. Если вы хотите добавить новые факты, напишите их явно в следующем сообщении.
```

Подсказку можно показывать над полем ввода или под последним ответом ИИ.

## 11. Панель параметров генерации

Панель располагается над полем ввода.

На desktop она может быть горизонтальной. На mobile — компактной, в виде раскрывающегося блока `Параметры статьи`.

### Поля панели

1. Стиль/тон.
2. Длина.
3. Композиция.
4. Количество абзацев.
5. Нужен заголовок.
6. Дополнительные инструкции.
7. Сброс настроек.

Язык не нужен, потому что проект работает только на русском.

Строгость к фактам не нужна как UI-параметр, потому что запрет на выдумывание фактов является системным правилом всегда.

## 12. Поле: стиль/тон

Тип: `select` или набор compact chips.

Значения:

| Value | Label |
|---|---|
| `neutral_news` | Нейтрально-новостной |
| `business` | Деловой |
| `light_magazine` | Лёгкий журнальный |
| `human_interest` | Human interest |

### Описания для UI

При выборе или наведении показывать короткое описание.

#### Нейтрально-новостной

Сдержанный информационный стиль без эмоциональных оценок.

#### Деловой

Более формальный стиль для корпоративных, экономических и профессиональных тем.

#### Лёгкий журнальный

Более живой и плавный стиль, но без рекламности и без выдуманных деталей.

#### Human interest

Фокус на человеке, ситуации или человеческом измерении новости, только на основе предоставленных фактов.

### Значение по умолчанию

`neutral_news`.

## 13. Поле: длина

Тип: `select`.

Значения:

| Value | Label | Target |
|---|---|---|
| `short` | 800–1500 символов | 1200–1500 по умолчанию |
| `medium` | 1501–2500 символов | около 2000 |
| `long` | 2501–4000 символов | около 3200 |
| `custom` | Своя длина | ручной ввод |

### Ручная длина

Если выбран `custom`, показать числовое поле:

- минимум: 800;
- максимум: 4000;
- единица: символы с пробелами.

### Системное правило

Длина является ориентиром, но модель не должна растягивать текст за счёт выдуманных фактов.

Если пользователь просит 4000 символов, а фактов хватает только на 1000 символов, модель должна написать около 1000 символов и при необходимости задать вопросы.

### Значение по умолчанию

`short`, целевой диапазон: 1200–1500 символов.

## 14. Поле: композиция

Тип: `select`.

Значения:

| Value | Label |
|---|---|
| `inverted_pyramid` | Перевёрнутая пирамида |
| `chronology` | Хронологическая структура |
| `fact_context_consequence` | Факт → контекст → последствия |
| `problem_reaction_consequence` | Проблема → реакция → последствия |
| `human_interest_structure` | Human interest |
| `explainer` | Explainer / объясняющая структура |
| `aida_no_cta` | AIDA без CTA |

### Описания для UI

#### Перевёрнутая пирамида

Главное — в начале, затем детали, контекст и второстепенная информация. Базовый формат для новости.

#### Хронологическая структура

События изложены по порядку. Подходит, когда важно показать развитие ситуации во времени.

#### Факт → контекст → последствия

Сначала главный факт, затем объяснение, затем возможное значение или последствия.

#### Проблема → реакция → последствия

Подходит для конфликтов, кризисов, общественных проблем и управленческих решений.

#### Human interest

Новость раскрывается через человеческий фокус, но без добавления неподтверждённых деталей.

#### Explainer / объясняющая структура

Помогает простым языком объяснить, что произошло, почему это важно и что известно.

#### AIDA без CTA

Внимание → интерес → детали → значимость. Без призывов к действию и рекламной подачи.

### Значение по умолчанию

`inverted_pyramid`.

## 15. Поле: количество абзацев

Тип: number input или compact stepper.

### Значения

- минимум: 2;
- максимум: 12;
- по умолчанию: 4.

### Правило при конфликте

Если длина и количество абзацев конфликтуют, длина важнее количества абзацев.

Пример: если пользователь выбрал 4 абзаца и 4000 символов, модель может сделать больше абзацев, если это нужно для читаемости. Но в промпте всё равно передаётся желаемое количество абзацев.

## 16. Переключатель: нужен заголовок

Тип: checkbox или switch.

По умолчанию включён.

В первой версии заголовок нужен всегда, потому что пользователь должен получать несколько вариантов заголовков. Но UI-переключатель можно оставить на будущее.

Если переключатель включён, ответ должен содержать несколько вариантов заголовков.

## 17. Дополнительные инструкции

Тип: textarea, компактное поле.

Placeholder:

```text
Например: сделать текст более официальным, избегать оценочных формулировок, не использовать слово «уникальный»...
```

## 18. Кнопка сброса настроек

Кнопка: `Сбросить настройки`.

Возвращает параметры к значениям:

- стиль: нейтрально-новостной;
- длина: 1200–1500 символов;
- композиция: перевёрнутая пирамида;
- абзацы: 4;
- заголовок: включён;
- дополнительные инструкции: пусто.

Настройки не нужно сохранять между сессиями.

## 19. Поле ввода материала

### Первичная генерация

Если в диалоге ещё нет версии статьи, поле ввода используется для сырого материала.

Placeholder:

```text
Вставьте сырой материал статьи, факты, тезисы или заметки...
```

### Доработка статьи

Если в диалоге уже есть статья, поле ввода используется как чат для правок.

Placeholder:

```text
Напишите, что изменить в последней версии статьи...
```

### Требования

- textarea должна автоматически увеличиваться по высоте до разумного предела;
- на мобильном не должна перекрывать весь экран;
- введённый текст не должен исчезать при ошибке отправки;
- кнопка отправки неактивна, если поле пустое и файл не выбран.

## 20. Загрузка `.docx`

### UI

Рядом с полем ввода должна быть кнопка:

```text
Прикрепить DOCX
```

или иконка скрепки с подписью.

### Поведение

1. Пользователь выбирает `.docx`.
2. Frontend отправляет файл на backend.
3. Backend извлекает текст.
4. Оригинальный файл удаляется после обработки.
5. Извлечённый текст подставляется в поле ввода или отправляется вместе с запросом.

### Ограничения

- Принимать только `.docx`.
- Не принимать `.doc`, `.pdf`, изображения и архивы.
- Если файл не `.docx`, показать ошибку:

```text
Можно загрузить только файл .docx
```

- Если извлечённый текст превышает лимит входа, показать ошибку:

```text
Текст из файла превышает лимит. Сократите материал или обратитесь к администратору.
```

## 21. Кнопка отправки

### Состояние по умолчанию

Кнопка: `Отправить` или `Создать статью`.

Для первого сообщения лучше использовать:

```text
Создать статью
```

Для последующих сообщений:

```text
Отправить правку
```

### Во время генерации

Кнопка должна быть заблокирована.

Текст кнопки:

```text
ИИ думает...
```

или

```text
Готовим материал...
```

## 22. Состояния генерации

Генерация не потоковая. Пользователь ждёт полный ответ.

Frontend должен показывать понятный статус.

### Возможные статусы

| Status | UI text |
|---|---|
| `queued` | Запрос в очереди... |
| `running` | ИИ готовит материал... |
| `completed` | Готово |
| `failed` | Не удалось получить ответ |
| `timeout` | Модель отвечает слишком долго |
| `cancelled` | Запрос отменён |

### Polling

Frontend должен периодически опрашивать backend по статусу job.

Рекомендуемый интервал:

- каждые 2 секунды первые 30 секунд;
- затем каждые 5 секунд.

### Блокировка повторных запросов

Пока у пользователя есть активная генерация в текущем диалоге, нельзя отправить новый запрос.

Показать сообщение:

```text
Дождитесь завершения текущей генерации.
```

## 23. Ошибки генерации

### Ошибка модели

```text
Не удалось получить ответ от модели. Попробуйте ещё раз.
```

### Таймаут

```text
Модель отвечает слишком долго. Материал не потерян — попробуйте повторить запрос.
```

### Некорректный ответ модели

```text
Модель вернула ответ в неожиданном формате. Попробуйте ещё раз или измените материал.
```

### Недостаточно фактов

Это не техническая ошибка. Модель должна вернуть короткий материал и вопросы.

Frontend показывает ответ как обычное сообщение ИИ.

## 24. Копирование ответа

Кнопка `Копировать` должна копировать полный текст ответа ИИ:

- заголовки;
- лид;
- статью;
- вопросы, если есть.

После копирования показать короткое подтверждение:

```text
Скопировано
```

## 25. Скачать TXT

Кнопка `Скачать TXT` должна запрашивать backend endpoint скачивания.

Файл должен содержать последний ответ ИИ в человекочитаемом виде.

Имя файла:

```text
article_<chat_id>_<version>.txt
```

или slug от названия диалога, если он безопасно формируется.

## 26. Версии статьи

Приложение должно хранить версии статьи.

### UI в MVP

Не нужен сложный интерфейс сравнения версий.

Достаточно:

- показывать последнюю версию в чате;
- у последней версии показывать кнопку `Откатиться к предыдущей версии`, если предыдущая версия существует;
- после отката добавить системное сообщение: `Восстановлена предыдущая версия статьи`.

### Правило памяти

ИИ при доработке должен работать только с последней версией статьи и новым сообщением пользователя.

Frontend должен показывать подсказку об этом пользователю.

## 27. Пустые состояния

### Нет активного диалога

```text
Выберите диалог или создайте новый, чтобы подготовить статью.
```

### Новый пустой диалог

```text
Вставьте материал, выберите параметры и нажмите «Создать статью».
```

### Нет результатов в админке

```text
Ничего не найдено.
```

## 28. Админка

URL prefix: `/admin`

Админка должна быть простой и функциональной.

## 28.1. Общая навигация админки

Разделы:

1. Пользователи.
2. Диалоги.
3. Промпты.
4. Настройки.
5. Логи генераций.

## 28.2. Пользователи

URL: `/admin/users`

### Список пользователей

Колонки:

- логин;
- роль;
- статус;
- дата создания;
- последний вход, если хранится;
- действия.

### Действия

- `Создать пользователя`;
- `Сменить пароль`;
- `Заблокировать` / `Разблокировать`;
- `Сделать админом` / `Сделать пользователем`, если нужно.

### Создание пользователя

Поля:

- логин;
- пароль;
- роль: user/admin.

Email не нужен.

## 28.3. Диалоги всех пользователей

URL: `/admin/chats`

### Список

Колонки:

- название диалога;
- пользователь;
- дата создания;
- дата последнего сообщения;
- количество сообщений;
- статус последней генерации.

### Просмотр диалога

Админ должен видеть:

- владельца диалога;
- сообщения пользователя;
- ответы ИИ;
- версии статьи;
- технические данные генераций, если они есть.

Админ не должен редактировать чужой диалог в MVP.

## 28.4. Промпты

URL: `/admin/prompts`

### Назначение

Админ редактирует основной мастер-промт.

### UI

- textarea с текущим мастер-промтом;
- кнопка `Сохранить`;
- подсказка по переменным подстановки.

### Переменные подстановки

Показать список доступных переменных:

- `{tone}`
- `{length}`
- `{paragraphs}`
- `{composition}`
- `{context}`
- `{source_material}`
- `{additional_instructions}`
- `{latest_article_version}`
- `{user_message}`

Фактический набор переменных должен быть синхронизирован с `PROMPTING_SPEC.md`.

### Ошибки

Если промпт пустой:

```text
Мастер-промт не может быть пустым.
```

## 28.5. Настройки

URL: `/admin/settings`

### Поля

- максимальный размер входного текста, символы;
- таймаут генерации, секунды;
- количество одновременных генераций;
- default max tokens;
- default temperature;
- default top_p;
- debug mode: включён/выключен;
- model base URL;
- model name;

API key не должен отображаться открытым текстом. Его лучше задавать через `.env`.

### Важные дефолты

- `max_input_chars`: 5000;
- `generation_timeout_seconds`: 180;
- `max_concurrent_generations`: 2;
- `model`: `Qwen/Qwen3-32B`, пока пользователь не укажет другое;
- `temperature`: 0.7;
- `top_p`: 0.8.

## 28.6. Логи генераций

URL: `/admin/logs`

### Список

Колонки:

- дата;
- пользователь;
- диалог;
- статус;
- входных символов;
- запрошенная длина;
- длительность;
- model name;
- HTTP status;
- ошибка, если есть.

### Просмотр log item

Если debug mode включён, админ может видеть:

- собранный prompt;
- параметры модели;
- технический ответ/ошибку.

Полные пользовательские тексты уже доступны через просмотр диалога, поэтому в логах не обязательно дублировать содержимое сообщений.

## 29. Валидация на frontend

Frontend должен выполнять базовую валидацию до отправки.

### Первичная генерация

Проверить:

- выбран активный диалог;
- текст или `.docx` не пустой;
- длина текста не превышает лимит;
- количество абзацев в допустимом диапазоне;
- длина статьи выбрана корректно.

### Доработка

Проверить:

- есть последняя версия статьи;
- сообщение пользователя не пустое;
- нет активной генерации.

Backend всё равно должен повторно валидировать все данные.

## 30. Responsive design

### Breakpoints

Рекомендуемые:

- mobile: до 767 px;
- tablet: 768–1023 px;
- desktop: от 1024 px.

### Mobile

На мобильном:

- sidebar скрыт за кнопкой меню;
- чат занимает почти весь экран;
- параметры статьи могут быть в collapsible-блоке;
- поле ввода закреплено внизу;
- кнопки должны быть достаточно крупными;
- таблицы админки должны превращаться в карточки или иметь горизонтальный скролл.

### Desktop

На desktop:

- sidebar слева;
- чат справа;
- панель параметров над composer;
- админка может использовать таблицы.

## 31. Accessibility

Минимальные требования:

- все поля имеют `label`;
- кнопки имеют понятный текст или `aria-label`;
- контраст текста достаточный;
- ошибки связаны с соответствующими полями;
- интерфейс доступен с клавиатуры;
- фокус виден.

## 34. JavaScript-модули

### `chat.js`

- отправка сообщений;
- блокировка формы во время генерации;
- обновление сообщений;
- переключение режима первичной генерации/доработки.

### `polling.js`

- опрос статуса generation job;
- обработка `queued`, `running`, `completed`, `failed`, `timeout`;
- подстановка готового ответа в чат.

### `copy.js`

- копирование текста ответа ИИ;
- показ состояния `Скопировано`.

### `upload.js`

- проверка расширения `.docx`;
- отправка файла;
- показ ошибок загрузки;
- подстановка извлечённого текста.

### `admin.js`

- подтверждения опасных действий;
- фильтры таблиц;
- раскрытие debug-информации.

## 35. CSS-рекомендации

Использовать обычный CSS без тяжёлых UI-библиотек.

Можно использовать CSS variables:

```css
:root {
  --color-bg: #f7f7f8;
  --color-surface: #ffffff;
  --color-text: #111827;
  --color-muted: #6b7280;
  --color-border: #e5e7eb;
  --color-primary: #2563eb;
  --radius-md: 12px;
  --radius-lg: 18px;
}
```

Допускается использовать минимальный CSS framework, если это сильно ускорит разработку, но предпочтительно не добавлять тяжёлые зависимости.

## 36. Требования к безопасности frontend

- Не показывать API key модели в интерфейсе.
- Не хранить токены модели в localStorage.
- Не доверять данным с frontend: backend валидирует всё повторно.
- Все пользовательские тексты выводить с HTML-экранированием.
- Если markdown-рендеринг будет добавлен, его нужно санитизировать.
- Админские страницы должны быть недоступны обычным пользователям.

## 37. Требования к markdown/форматированию ответа ИИ

В первой версии можно отображать ответ как plain text с сохранением переносов строк.

Если используется markdown:

- разрешить только базовое форматирование;
- санитизировать HTML;
- не выполнять скрипты;
- не вставлять непроверенный HTML.

Рекомендуется MVP-вариант:

```html
<pre class="message-text"></pre>
```

или CSS:

```css
.message-text {
  white-space: pre-wrap;
}
```

## 38. Критерии приёмки frontend

Frontend считается готовым для MVP, если:

1. Пользователь может войти по логину и паролю.
2. Пользователь видит список своих диалогов.
3. Пользователь может создать новый диалог с обязательным названием.
4. Пользователь может ввести материал вручную.
5. Пользователь может загрузить `.docx`.
6. Пользователь может выбрать стиль, длину, композицию и количество абзацев.
7. Пользователь может отправить материал на генерацию.
8. Во время генерации пользователь видит статус ожидания.
9. Пользователь получает ответ ИИ в чате.
10. Пользователь может продолжить диалог и доработать последнюю версию статьи.
11. Пользователь видит подсказку, что ИИ помнит только последнюю версию статьи.
12. Пользователь может скопировать ответ.
13. Пользователь может скачать ответ в `.txt`.
14. Пользователь может откатиться к предыдущей версии, если она есть.
15. Админ может открыть админку.
16. Админ может создавать и блокировать пользователей.
17. Админ может видеть все диалоги с указанием пользователей.
18. Админ может редактировать мастер-промт.
19. Админ может менять лимит входного текста.
20. Админ может просматривать логи генераций.
21. Интерфейс удобно работает на мобильном экране.
22. Ошибки модели, таймауты и превышение лимита отображаются понятным текстом.

## 39. Что не входит в первую версию

В MVP не делать:

- тёмную тему;
- переименование диалогов;
- удаление диалогов;
- сложное сравнение версий;
- экспорт `.docx`;
- загрузку `.pdf`;
- загрузку изображений;
- самостоятельную регистрацию;
- email-уведомления;
- публичные ссылки на статьи;
- real-time streaming ответа модели;
- полноценный WYSIWYG-редактор статьи;
- интеграцию с CMS.

## 40. Итоговое указание для Codex

Codex должен реализовать frontend как часть единого FastAPI-приложения.

Главная цель — не визуальная сложность, а рабочий, понятный и мобильный интерфейс, в котором PR-специалист может быстро:

1. создать диалог;
2. вставить факты;
3. выбрать параметры статьи;
4. получить заголовки, лид и текст;
5. доработать последнюю версию через чат;
6. скопировать или скачать результат.
