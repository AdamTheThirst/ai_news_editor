# PRODUCT_REQUIREMENTS.md

# AI-редактор новостных статей — продуктовые требования

## 1. Назначение документа

Этот документ описывает продуктовые требования к веб-приложению «AI-редактор статей». Документ предназначен для Codex и разработчика, который будет реализовывать проект итерациями.

Документ фиксирует:

- целевую аудиторию;
- роли пользователей;
- основные пользовательские сценарии;
- требования к генерации статей;
- требования к интерфейсу;
- ограничения по фактам и работе модели;
- требования к админке;
- требования к истории диалогов;
- требования к загрузке `.docx`;
- требования к обработке ошибок;
- критерии приёмки MVP.

Техническая архитектура, схема базы данных, API-контракты и детали деплоя будут описаны в отдельных `.md`-файлах.

---

## 2. Краткое описание продукта

Продукт — многопользовательский веб-сервис для подготовки русскоязычных новостных и PR-материалов с помощью локально/частно развёрнутой LLM-модели, доступной через OpenAI-compatible API.

Пользователь вводит сырой материал статьи или набор фактов, выбирает параметры будущего текста и отправляет задачу модели. Система возвращает:

1. несколько вариантов заголовков;
2. лид;
3. готовую статью;
4. вопросы к пользователю, если данных недостаточно.

После генерации пользователь может продолжать диалог с ИИ и просить доработать последнюю версию статьи.

Главное ограничение продукта: **модель не имеет права выдумывать факты, даты, имена, цифры, цитаты, должности, причинно-следственные связи и любые сведения, которых нет в пользовательском материале или в явно заданном контексте**.

---

## 3. Целевая аудитория

Основной пользователь: **PR-специалист**.

Типовые задачи пользователя:

- превратить набор фактов в новостную заметку;
- подготовить текст для сайта, СМИ, корпоративного блога или рассылки;
- переписать материал в другом стиле;
- сократить или расширить статью в пределах доступных фактов;
- сделать лид сильнее;
- получить несколько вариантов заголовков;
- адаптировать материал под новостную структуру;
- доработать уже сгенерированную статью в формате чата.

---

## 4. Язык продукта

### 4.1. Язык интерфейса

Интерфейс приложения должен быть на русском языке.

### 4.2. Язык генерируемых статей

Генерация в первой версии выполняется только на русском языке.

Отдельный выбор языка в интерфейсе не нужен.

---

## 5. Платформа и формат продукта

Приложение должно быть:

- веб-приложением;
- многопользовательским;
- доступным через интернет на VPS;
- рассчитанным на Ubuntu 22.x;
- разворачиваемым через Python `venv`, без Docker в первой версии;
- ориентированным на мобильный интерфейс в первую очередь;
- с нормальным UI/UX, а не прототипным интерфейсом Streamlit/Gradio.

Рекомендуемый стек для MVP:

- Python;
- FastAPI;
- SQLite;
- Jinja2 templates;
- HTMX;
- Alpine.js или минимальный vanilla JS;
- CSS без тяжёлого frontend-фреймворка либо с лёгкой utility-структурой;
- OpenAI Python SDK для подключения модели.

Frontend и backend должны находиться в одном приложении.

---

## 6. Роли пользователей

В системе должны быть две роли:

1. `user` — обычный пользователь;
2. `admin` — администратор.

### 6.1. Обычный пользователь

Обычный пользователь может:

- войти в систему по логину и паролю;
- видеть только свои диалоги;
- создавать новые диалоги;
- вводить сырой материал вручную;
- загружать `.docx`;
- указывать параметры будущей статьи;
- запускать генерацию;
- видеть статус генерации;
- получать результат;
- продолжать диалог с ИИ;
- скачивать результат в `.txt`;
- копировать результат в буфер обмена;
- откатиться к предыдущей версии статьи, если такая версия есть.

Обычный пользователь не может:

- регистрироваться самостоятельно;
- видеть чужие диалоги;
- видеть мастер-промт;
- видеть debug-промпт;
- менять системные настройки;
- создавать других пользователей.

### 6.2. Администратор

Администратор может:

- входить в систему по логину и паролю;
- создавать пользователей;
- блокировать пользователей;
- менять пароли пользователей;
- видеть список пользователей;
- видеть все диалоги с указанием пользователей;
- открывать любой диалог;
- менять мастер-промт;
- менять лимит входного материала;
- менять дефолтные настройки генерации;
- видеть debug-промпт, который отправляется модели;
- видеть технические логи генераций;
- видеть ошибки модели;
- при необходимости настраивать endpoint модели, model name и часть параметров подключения через конфиг или админку, если это будет удобно реализовать.

---

## 7. Регистрация и авторизация

### 7.1. Регистрация

Свободная регистрация пользователей не нужна.

Пользователей создаёт только администратор.

Для пользователя достаточно:

- логина;
- пароля;
- роли;
- статуса активности.

Email, подтверждение email, восстановление пароля по email и OAuth в первой версии не нужны.

### 7.2. Вход

Пользователь входит по логину и паролю.

### 7.3. Пароли

Пароли должны храниться только в виде безопасного хеша.

Запрещено хранить пароли в открытом виде.

### 7.4. Сессии

Приложение должно поддерживать web-сессии.

Если сессия истекла, пользователь должен быть перенаправлен на страницу входа.

---

## 8. Главный пользовательский сценарий

Основной сценарий:

1. Пользователь входит в приложение.
2. Открывает главный экран.
3. Нажимает «Новый диалог».
4. Указывает обязательное название диалога.
5. Вводит сырой материал статьи вручную или загружает `.docx`.
6. При необходимости добавляет контекст.
7. Выбирает параметры статьи:
   - стиль/тон;
   - длину;
   - композицию;
   - количество абзацев;
   - необходимость заголовков и лида включена по умолчанию;
   - дополнительные инструкции, если поле будет реализовано.
8. Нажимает кнопку отправки.
9. Интерфейс показывает, что ИИ думает или задача находится в очереди.
10. Backend собирает промпт из мастер-промта, параметров пользователя, контекста и исходного материала.
11. Backend отправляет запрос в модель через OpenAI-compatible API.
12. Система сохраняет результат.
13. Пользователь получает:
    - несколько вариантов заголовков;
    - лид;
    - статью;
    - вопросы к пользователю, если данных недостаточно.
14. Пользователь может скопировать результат или скачать `.txt`.
15. Пользователь может написать в чат просьбу доработать последнюю версию статьи.
16. Модель дорабатывает именно последнюю версию статьи, учитывая исходные факты и новые явные указания пользователя.

---

## 9. Диалоги и история

### 9.1. Диалоги

Диалог — это отдельная рабочая сессия пользователя по одному материалу или теме.

У каждого диалога должно быть обязательное название.

Название задаёт пользователь при создании диалога.

### 9.2. История диалогов

Пользователь должен видеть список своих диалогов.

В первой версии не нужны:

- переименование диалогов;
- удаление диалогов.

### 9.3. История сообщений

В диалоге должны сохраняться:

- исходный пользовательский ввод;
- параметры генерации;
- ответы модели;
- последующие сообщения пользователя;
- последующие ответы модели;
- системные статусы генерации, если они нужны для отображения.

### 9.4. Последняя версия статьи

ИИ должен работать с последней версией статьи.

В интерфейсе нужно показать пользователю подсказку:

> ИИ помнит только последнюю версию статьи в этом диалоге. Если вы вручную переносите правки в другом месте, вставьте обновлённый текст в чат.

Формулировку можно адаптировать под UI.

---

## 10. Версии статей

Система должна хранить версии статьи автоматически.

Новая версия создаётся:

- после первой генерации;
- после каждой доработки статьи моделью.

Для MVP достаточно простой логики:

- хранить предыдущие версии в базе;
- показывать в UI текущую версию;
- дать кнопку «Откатиться к предыдущей версии», если такая версия существует.

Не требуется:

- визуальный diff;
- подсветка изменений;
- ручное сравнение версий;
- именование версий пользователем.

---

## 11. Ввод материала

### 11.1. Ручной ввод

Пользователь может вставить сырой материал статьи в текстовое поле.

Материал может быть:

- набором фактов;
- черновиком;
- заметками;
- тезисами;
- фрагментом пресс-релиза;
- неструктурированным текстом.

### 11.2. Загрузка `.docx`

Пользователь может загрузить `.docx`.

Требования:

- backend извлекает текст из `.docx`;
- извлечённый текст используется как исходный материал;
- сам файл после извлечения текста удаляется;
- сохранять файл на сервере не нужно;
- сохраняется только извлечённый текст как часть сообщения/диалога;
- если извлечь текст не удалось, пользователь получает понятную ошибку.

### 11.3. Единый блок материала

В первой версии не нужно делать отдельные поля для:

- фактов;
- цитат;
- бэкграунда;
- запрещённых формулировок.

Всё вводится одним блоком.

### 11.4. Опциональный контекст

Дополнительно должно быть поле «Контекст».

Контекст заполняется опционально.

Примеры контекста:

- где будет опубликован материал;
- для кого материал;
- какой инфоповод важнее;
- что нужно подчеркнуть;
- какие ограничения есть у публикации.

Контекст не должен превращаться в источник новых фактов, если пользователь не указал его как фактическую информацию.

---

## 12. Лимиты входного материала

По умолчанию максимальный объём входного материала — **5000 символов**.

Администратор должен иметь возможность менять этот лимит в админке.

Лимит применяется к:

- ручному вводу;
- тексту, извлечённому из `.docx`.

Если материал превышает лимит:

- система не должна отправлять его в модель;
- пользователь должен получить понятное сообщение;
- желательно показать текущий лимит и фактический размер текста.

Пример сообщения:

> Материал слишком длинный: 6420 символов. Текущий лимит — 5000 символов. Сократите текст или обратитесь к администратору.

---

## 13. Параметры генерации статьи

Параметры должны отображаться над или рядом с окном ввода, с приоритетом на удобство мобильного интерфейса.

### 13.1. Стиль/тон

В первой версии доступны стили:

1. **Нейтрально-новостной** — сухая и сбалансированная подача, без эмоциональных оценок.
2. **Деловой** — официальный, структурный, подходит для корпоративных и экономических новостей.
3. **Лёгкий журнальный** — более живой стиль, но без нарушения фактической строгости.
4. **Human interest** — фокус на людях, ситуации и значении события для аудитории, без выдуманных деталей.

Пользователь не может создавать собственные стили в первой версии.

### 13.2. Длина статьи

Длина задаётся в символах.

Нужны пресеты:

1. **Короткая**: 800–1500 символов.
2. **Средняя**: 1501–2500 символов.
3. **Длинная**: 2501–4000 символов.

Длина по умолчанию: **1200–1500 символов**.

Если пользователь просит длинный текст, но фактов хватает только на короткий материал, модель должна написать короткий материал и не растягивать текст водой или выдумками.

Пример правила:

> Если фактов достаточно только для статьи примерно на 1000 символов, а пользователь выбрал 4000 символов, модель должна вернуть статью примерно на 1000 символов и при необходимости добавить вопросы о недостающих данных.

### 13.3. Количество абзацев

Пользователь может задать количество абзацев числом.

По умолчанию: **4 абзаца**.

Если выбранная длина конфликтует с количеством абзацев, приоритет имеет длина и фактическая полнота материала.

Пример:

- пользователь выбрал 4 абзаца и 4000 символов;
- фактов достаточно только на 1200 символов;
- модель должна вернуть короткий текст, не выдумывая детали.

### 13.4. Композиция статьи

В первой версии доступны композиции:

1. **Перевёрнутая пирамида**  
   Главное в начале, затем детали, контекст и дополнительные сведения. Структура по умолчанию.

2. **Хронологическая структура**  
   События излагаются в порядке развития.

3. **Факт → контекст → последствия**  
   Сначала ключевой факт, затем объяснение контекста и возможных последствий.

4. **Проблема → реакция → последствия**  
   Подходит для конфликтов, кризисов, спорных решений и общественных ситуаций.

5. **Human interest**  
   Материал строится вокруг человеческого измерения события, но без выдумывания персонажей, эмоций или деталей.

6. **Explainer / объясняющая структура**  
   Текст объясняет, что произошло, почему это важно и что известно из предоставленных фактов.

7. **AIDA без CTA**  
   Адаптированная новостная структура: внимание → интерес → детали → значимость. Запрещены рекламные призывы и CTA.

У каждой композиции в интерфейсе должно быть короткое описание.

### 13.5. Заголовки и лид

По умолчанию модель должна генерировать:

- несколько вариантов заголовков;
- лид;
- основную статью.

Отдельный переключатель «генерировать заголовок» в MVP не обязателен, потому что заголовки и лид являются обязательной частью результата.

### 13.6. Дополнительные инструкции

Желательно предусмотреть поле «Дополнительные инструкции».

Оно может использоваться для указаний вроде:

- «сделай текст суше»;
- «не использовать слово X»;
- «подчеркнуть региональный аспект»;
- «не делать вывод в конце».

Дополнительные инструкции не должны разрешать модели выдумывать факты.

---

## 14. Требования к результату генерации

Модель должна возвращать результат в понятной структуре:

```text
Заголовки:
1. ...
2. ...
3. ...

Лид:
...

Статья:
...

Вопросы к пользователю:
1. ...
2. ...
```

Если вопросов нет, блок «Вопросы к пользователю» можно не показывать или показать «Вопросов нет».

### 14.1. Заголовки

Нужно генерировать несколько вариантов заголовков.

Рекомендуемое количество: 3–5.

Заголовки должны быть:

- фактическими;
- без кликбейта;
- без неподтверждённых обещаний;
- без фактов, которых нет в исходном материале.

### 14.2. Лид

Лид должен кратко отвечать на ключевые вопросы материала:

- что произошло;
- кто участник события;
- где/когда произошло, если это есть в исходных данных;
- почему это важно, если это следует из исходных данных.

Если каких-то данных нет, модель не должна их придумывать.

### 14.3. Статья

Статья должна соответствовать:

- выбранному стилю;
- выбранной композиции;
- выбранной длине, если хватает фактов;
- выбранному количеству абзацев, если это не конфликтует с длиной и фактами;
- правилам новостной подачи;
- запрету на CTA;
- запрету на выдумывание фактов.

### 14.4. Вопросы к пользователю

Если данных недостаточно, модель должна задать вопросы.

Вопросы нужны, когда:

- невозможно уверенно написать заявленную длину;
- отсутствуют ключевые факты;
- есть противоречия в исходном материале;
- пользователь просит доработку, требующую новых данных;
- непонятно, кого, где или когда касается событие;
- есть риск сделать неподтверждённое утверждение.

---

## 15. Фактические ограничения

Это одно из главных требований продукта.

Модель должна использовать только:

- исходный материал пользователя;
- текст, извлечённый из `.docx`;
- опциональный контекст пользователя;
- последнюю версию статьи в текущем диалоге;
- явные новые факты, которые пользователь добавил в последующих сообщениях.

Модель не должна:

- обращаться к интернету;
- проводить фактчекинг через внешние источники;
- добавлять сведения из собственных знаний;
- придумывать даты;
- придумывать имена;
- придумывать должности;
- придумывать цифры;
- придумывать географию;
- придумывать цитаты;
- придумывать причинно-следственные связи;
- добавлять экспертные оценки, если их нет в материале;
- превращать предположения в утверждения;
- растягивать текст водой ради заданного объёма.

Если пользователь просит добавить факт, которого нет в исходных данных, модель должна отказаться добавлять его как установленный факт и попросить пользователя предоставить данные.

Пример поведения:

Пользователь:

> Добавь, что компания стала лидером рынка.

Если такого факта нет в исходном материале, ответ должен быть примерно таким:

> Я не могу добавить утверждение о лидерстве на рынке без подтверждения в исходных данных. Если это действительно нужно включить, добавьте источник или формулировку, которую можно использовать.

---

## 16. CTA и маркетинговые элементы

Проект предназначен для новостных и PR-материалов, но не для рекламных лендингов.

Модель должна избегать:

- прямых призывов к действию;
- рекламных обещаний;
- фраз вроде «покупайте», «закажите», «переходите», «оставьте заявку»;
- финальных CTA-блоков;
- чрезмерно рекламной подачи.

Композиция AIDA допускается только в адаптированном новостном варианте и **без CTA**.

---

## 17. Доработка статьи через чат

После первой генерации пользователь может писать в чат просьбы:

- «сделай короче»;
- «сделай деловым стилем»;
- «перепиши лид»;
- «добавь ещё один вариант заголовка»;
- «измени структуру на перевёрнутую пирамиду»;
- «убери последний абзац»;
- «сделай текст проще»;
- «добавь вот этот факт: ...».

Модель должна дорабатывать последнюю версию статьи.

Если пользователь добавляет новый факт в сообщении, этот факт можно использовать.

Если пользователь просит добавить факт, но сам факт не предоставляет, модель должна попросить данные.

После каждой доработки создаётся новая версия статьи.

---

## 18. Интерфейс пользователя

### 18.1. Общий принцип

Интерфейс должен быть похож на упрощённый ChatGPT:

- список диалогов;
- центральная область сообщений;
- поле ввода;
- параметры генерации над полем ввода или в компактной панели;
- состояние генерации;
- кнопки действий у результата.

Приоритет — мобильный UI.

### 18.2. Страницы обычного пользователя

Минимально нужны:

1. Страница входа.
2. Главная страница со списком диалогов и активным чатом.
3. Страница/модальное окно создания нового диалога.
4. Экран активного диалога.

### 18.3. Компоненты активного диалога

В активном диалоге должны быть:

- название диалога;
- список сообщений;
- текущая версия статьи;
- блок параметров генерации;
- поле сырого материала при первом запуске;
- поле сообщения для последующих доработок;
- кнопка отправки;
- индикатор генерации;
- кнопка копирования;
- кнопка скачивания `.txt`;
- кнопка отката к предыдущей версии, если есть предыдущая версия.

### 18.4. Параметры над вводом

Нужны поля:

- стиль/тон;
- длина;
- композиция;
- количество абзацев;
- контекст;
- дополнительные инструкции;
- сброс настроек по умолчанию.

Не нужны:

- выбор языка;
- настройка температуры;
- настройка top_p;
- настройка строгости к фактам.

### 18.5. Состояние генерации

Так как ответ модели не потоковый, интерфейс должен показывать состояние ожидания.

Минимально:

- кнопка отправки блокируется;
- показывается текст «ИИ думает…»;
- если задача в очереди, показывается «Задача в очереди…»;
- если идёт генерация, показывается «ИИ пишет статью…»;
- если произошла ошибка, показывается понятное сообщение.

Можно добавить простой loader/spinner.

---

## 19. Очередь генераций

Система должна учитывать, что одновременно может работать до 30 пользователей.

Чтобы не перегружать модель:

- один пользователь не должен запускать несколько активных генераций одновременно;
- глобальное число параллельных генераций должно быть ограничено;
- остальные задачи должны ждать в очереди;
- состояние задачи должно сохраняться в базе.

Рекомендуемые статусы задачи:

- `queued`;
- `running`;
- `succeeded`;
- `failed`;
- `cancelled`, если будет реализована отмена.

Для MVP можно реализовать простую очередь на SQLite и background worker внутри FastAPI-процесса.

---

## 20. Подключение модели

Модель подключается через OpenAI-compatible API.

Минимальный пример подключения:

```python
from openai import OpenAI

client = OpenAI(
    base_url="https://ai...",
    api_key="sk-..."
)

chat_response = client.chat.completions.create(
    model="Qwen/Qwen3-32B",
    messages=[
        {"role": "system", "content": "..."},
        {"role": "user", "content": "..."}
    ],
    max_tokens=200,
    temperature=0.7,
    top_p=0.8
)
```

В коде нельзя хардкодить реальные:

- `base_url`;
- `api_key`;
- `model`.

Они должны задаваться через переменные окружения или настройки приложения.

Пример переменных:

```env
LLM_BASE_URL=https://ai.example.com/v1
LLM_API_KEY=change-me
LLM_MODEL=Qwen/Qwen3-32B
LLM_TIMEOUT_SECONDS=180
```

Параметры `temperature` и `top_p` не показываются пользователю.

Для строгой новостной генерации рекомендуется использовать более низкую температуру, чем в тестовом примере, но точные значения будут зафиксированы в `PROMPTING_SPEC.md` или `MODEL_ADAPTER.md`.

---

## 21. Ошибки модели и таймауты

Если модель долго отвечает или падает, система должна:

- остановить ожидание по таймауту;
- сохранить статус задачи как `failed`;
- показать пользователю понятную ошибку;
- не терять исходный материал и параметры;
- дать возможность повторить генерацию;
- сохранить техническую информацию об ошибке для админа.

Пример сообщения пользователю:

> Модель не ответила за отведённое время. Материал и настройки сохранены, попробуйте повторить генерацию позже.

Пользователю не нужно показывать stack trace, токены, endpoint, полный prompt или технические детали.

---

## 22. Технические логи генераций

Система должна хранить технические логи генераций.

Логи нужны для диагностики.

Рекомендуется хранить:

- ID пользователя;
- ID диалога;
- ID задачи генерации;
- время создания задачи;
- время начала обработки;
- время завершения;
- статус;
- длительность;
- размер входного текста в символах;
- выбранную длину;
- выбранный стиль;
- выбранную композицию;
- количество абзацев;
- название модели;
- HTTP-статус ответа модели, если есть;
- краткое сообщение об ошибке, если есть.

Не обязательно хранить полный prompt в технических логах, потому что диалоги и debug-промпты доступны отдельно. Если полный prompt хранится, он должен быть доступен только админу.

## 23. Админка

### 23.1. Разделы админки

В админке нужны разделы:

1. Пользователи.
2. Системные настройки.
3. Мастер-промт.
4. Диалоги пользователей.
5. Технические логи генераций.

### 23.2. Пользователи

Админ может:

- создать пользователя;
- задать логин;
- задать временный пароль;
- выбрать роль;
- заблокировать пользователя;
- разблокировать пользователя;
- сменить пароль;
- видеть дату создания пользователя;
- видеть дату последнего входа, если это удобно реализовать.

### 23.3. Системные настройки

Админ может менять:

- максимальный размер входного материала;
- дефолтный диапазон длины статьи;
- дефолтное количество абзацев;
- таймаут модели;
- лимит параллельных генераций;
- возможно `LLM_BASE_URL`, `LLM_MODEL`, если это будет реализовано через базу, а не только через `.env`.

API key модели лучше хранить в `.env`, а не редактировать через web-интерфейс в MVP.

### 23.4. Мастер-промт

Мастер-промт редактируется через админку.

Промпт должен поддерживать подстановки параметров.

Примеры переменных:

```text
{tone}
{length_range}
{paragraph_count}
{composition}
{composition_description}
{context}
{additional_instructions}
{source_material}
{latest_article_version}
```

Полная логика промптов будет описана в `PROMPTING_SPEC.md`.

### 23.5. Debug prompt

Админ должен иметь возможность видеть полный prompt, который был отправлен модели.

Обычный пользователь не должен видеть debug prompt.

## 24. Скачивание и копирование

### 24.1. Копирование

У результата должна быть кнопка «Копировать».

Она копирует в буфер обмена:

- заголовки;
- лид;
- статью;
- возможно вопросы к пользователю, если они отображаются в результате.

### 24.2. Скачивание TXT

У результата должна быть кнопка «Скачать TXT».

Файл должен содержать:

- название диалога;
- дату генерации;
- заголовки;
- лид;
- статью;
- вопросы к пользователю, если есть.

Экспорт в `.docx` в первой версии не нужен.

## 25. Приватность и доступ к данным

Минимальные требования:

- пользователь видит только свои диалоги;
- админ видит все диалоги с указанием пользователей;
- пароли хранятся только в виде хеша;
- `.docx` удаляется после извлечения текста;
- загруженные файлы не должны быть публично доступны;
- debug prompt доступен только админу;
- системные настройки доступны только админу;
- технические ошибки не показываются обычным пользователям в сыром виде.

---

## 26. Что не входит в MVP

В MVP не входит:

- свободная регистрация;
- email;
- восстановление пароля по email;
- OAuth;
- удаление диалогов пользователем;
- переименование диалогов;
- экспорт в `.docx`;
- загрузка PDF;
- загрузка TXT отдельным файлом;
- поддержка других языков;
- интернет-фактчекинг;
- внешние источники;
- подключение CMS;
- визуальный diff версий;
- сложная аналитика;
- платежи;
- команды/организации;
- персональные стили пользователя;
- настройка температуры пользователем;
- Docker-деплой;
- React SPA, если выбран простой стек FastAPI + templates + HTMX.

## 27. Нефункциональные требования

### 27.1. Производительность

Ожидаемая нагрузка: до 30 пользователей.

Типичный размер статьи: 800–2000 символов.

Максимальный размер входного материала по умолчанию: 5000 символов.

### 27.2. Надёжность

Система должна:

- не терять пользовательский ввод при ошибке модели;
- сохранять статусы задач генерации;
- сохранять успешные результаты;
- логировать ошибки;
- корректно обрабатывать таймауты.

### 27.3. Удобство

Интерфейс должен быть:

- русскоязычным;
- понятным для PR-специалиста;
- удобным на мобильном экране;
- без технических терминов для обычного пользователя;
- с понятными подсказками по композициям.

### 27.4. Безопасность

Система должна:

- защищать маршруты авторизацией;
- разделять доступы `user` и `admin`;
- хешировать пароли;
- не раскрывать API key модели;
- не показывать чужие диалоги обычным пользователям.

## 28. Критерии приёмки MVP

MVP считается готовым, если выполняются следующие условия.

### 28.1. Авторизация

- Админ может войти.
- Админ может создать пользователя.
- Пользователь может войти.
- Пользователь не видит чужие диалоги.
- Админ видит все диалоги.

### 28.2. Создание статьи

- Пользователь может создать новый диалог с обязательным названием.
- Пользователь может вставить сырой материал вручную.
- Пользователь может загрузить `.docx`.
- Система извлекает текст из `.docx` и удаляет файл.
- Пользователь может выбрать стиль, длину, композицию и количество абзацев.
- Система отправляет запрос в модель через OpenAI-compatible API.
- Пользователь видит состояние ожидания.
- Пользователь получает заголовки, лид, статью и вопросы при необходимости.

### 28.3. Ограничения фактов

- Промпт явно запрещает выдумывать факты.
- При нехватке данных модель не растягивает текст искусственно.
- При просьбе добавить неподтверждённый факт модель просит пользователя дать этот факт явно.

### 28.4. Доработка

- Пользователь может продолжить диалог.
- Модель дорабатывает последнюю версию статьи.
- После доработки создаётся новая версия.
- Можно откатиться к предыдущей версии.

### 28.5. Экспорт

- Можно скопировать результат.
- Можно скачать результат в `.txt`.

### 28.6. Админка

- Админ может управлять пользователями.
- Админ может менять мастер-промт.
- Админ может менять лимит входного материала.
- Админ может видеть debug prompt.
- Админ может видеть технические логи генераций.

### 28.7. Ошибки

- При таймауте модели пользователь получает понятное сообщение.
- Исходный материал не теряется.
- Ошибка сохраняется в техническом логе.
- Пользователь может повторить генерацию.

## 30. Главный принцип разработки

При любых неоднозначностях Codex должен отдавать приоритет следующим правилам:

1. Продукт предназначен для русскоязычных новостных/PR-материалов.
2. Нельзя выдумывать факты.
3. Если фактов мало, текст должен быть короче, а не водянистее.
4. Пользователь видит только свои данные.
5. Админ видит все данные и настройки.
6. Интерфейс должен быть простым и мобильным.
7. MVP должен быть реализуемым без Docker и без сложного frontend-стека.
8. Все секреты модели должны храниться безопасно, без хардкода в коде.
