# CODEX_TASKS.md

## 1. Назначение документа

Этот файл — основной рабочий план для Codex.

Codex должен использовать его как пошаговую инструкцию по созданию проекта AI-редактора статей.

Проект пишется итерациями. Не нужно пытаться реализовать всё одним большим изменением. Каждая итерация должна давать проверяемый результат.

---

## 2. Что строим

Нужно создать многопользовательский веб-сервис для генерации и доработки русскоязычных новостных статей на базе локальной/частной LLM-модели Qwen, доступной через OpenAI-compatible API.

Пользователь:

1. входит по логину и паролю;
2. создаёт диалог;
3. задаёт обязательное название диалога;
4. вставляет сырой материал или загружает `.docx`;
5. опционально добавляет контекст;
6. выбирает тон, длину, композицию и количество абзацев;
7. запускает генерацию;
8. получает варианты заголовков, лид, статью и вопросы;
9. может дорабатывать последнюю версию статьи через чат;
10. может копировать результат и скачать TXT.

Администратор:

1. создаёт пользователей;
2. блокирует пользователей;
3. меняет пароли;
4. видит все диалоги всех пользователей;
5. редактирует мастер-промпт;
6. меняет лимиты и параметры генерации;
7. видит debug-промпты и технические логи;
8. проверяет подключение к модели.

## 4. Технологические решения

Использовать:

- Python 3.10+;
- FastAPI;
- SQLite;
- SQLAlchemy;
- Jinja2 templates;
- HTMX и/или минимальный vanilla JS;

- OAuth;
- интернет-поиск;
- фактчекинг через внешние источники.

Frontend должен быть server-rendered и простым для деплоя через `venv`.

## 5. Главные ограничения продукта

Обязательные правила:

1. Интерфейс только на русском языке.
2. Статьи генерируются только на русском языке.
3. Пользователь не регистрируется сам — аккаунты создаёт админ.
4. Пароли хранятся только в виде хеша.
5. Обычный пользователь видит только свои диалоги.
6. Админ видит все диалоги с указанием пользователей.
7. `.docx` удаляется после извлечения текста.
8. Модель использует только материал пользователя и контекст.
9. Модель не должна выдумывать факты.
10. Если данных мало, статья должна быть короче запрошенной длины.
11. CTA запрещены.
12. Debug-промпты доступны только админу.
13. API-ключ модели нельзя показывать в UI и логах.
14. Приложение разворачивается на Ubuntu 22.x через `venv`, systemd и Nginx.

## 30. Главный риск проекта

Главный риск — модель может начать выдумывать факты.

Поэтому Codex должен особенно внимательно реализовать:

- `prompt_builder.py`;
- технические ограничения поверх мастер-промпта;
- доработку только последней версии;
- отказ от добавления неподтверждённых фактов;
- вопросы пользователю при недостатке данных.

Даже если админ изменит мастер-промпт, код должен добавлять обязательные ограничения.

---

## 31. Второй риск проекта

Второй риск — утечка пользовательских данных между аккаунтами.

Поэтому Codex должен во всех routes и services проверять:

```text
object.user_id == current_user.id
```

для обычных пользователей.

Администраторский доступ должен идти через отдельные admin routes.

---

## 32. Третий риск проекта

Третий риск — нестабильность модели или долгие ответы.

Поэтому нужны:

- `generation_jobs`;
- статусы;
- timeout;
- polling;
- technical logs;
- retry by user;
- понятное сообщение об ошибке;
- сохранение исходного материала и параметров.

---

## 33. Финальное напоминание для Codex

Писать проект нужно как production-ready MVP, а не как одноразовый demo script.

Код должен быть:

- модульным;
- тестируемым;
- понятным;
- безопасным;
- без лишних зависимостей;
- без сложной frontend-сборки;
- готовым к запуску на Ubuntu 22.x через `venv`.
