# ARCHITECTURE.md

# Архитектура проекта «Редактор статей»

## 1. Назначение документа

Этот документ описывает техническую архитектуру веб-приложения «Редактор статей» для Codex. Документ фиксирует выбранный стек, основные модули, взаимодействие компонентов, хранение данных, подключение локальной LLM-модели через OpenAI-compatible API, обработку очереди генераций и принципы развёртывания на VPS.

Проект должен разрабатываться итерациями. Архитектура должна быть достаточно простой для MVP, но не должна мешать дальнейшему развитию приложения.

---

## 2. Краткое описание системы

«Редактор статей» — многопользовательское веб-приложение для PR-специалистов, которое превращает сырой материал, набор фактов или текст из `.docx` в новостную статью на русском языке.

Пользователь:

1. Входит в систему по логину и паролю.
2. Создаёт диалог с обязательным названием.
3. Вставляет сырой материал вручную или загружает `.docx`.
4. При необходимости добавляет контекст.
5. Выбирает стиль, длину, композицию и количество абзацев.
6. Отправляет материал в локальную LLM-модель.
7. Получает несколько вариантов заголовков, лид и статью.
8. Дорабатывает материал через чат.
9. Копирует результат или скачивает `.txt`.

Администратор:

1. Создаёт пользователей и управляет ими.
2. Видит все диалоги всех пользователей.
3. Редактирует мастер-промт.
4. Меняет системные лимиты.
5. Видит debug-информацию по запросам к модели.
6. Видит технические логи генераций.

## 3. Выбранный стек

### Backend

- Python 3.11+
- FastAPI
- SQLAlchemy 2.x
- SQLite
- Alembic, если Codex сочтёт миграции полезными для проекта
- Jinja2 templates
- python-multipart для загрузки файлов
- python-docx для чтения `.docx`
- passlib или argon2-cffi/bcrypt для хеширования паролей
- itsdangerous или серверные cookie-сессии для авторизации
- openai Python SDK для подключения к OpenAI-compatible vLLM API
- pytest для тестов

### Frontend

Приложение должно быть выполнено как единый Python-проект без отдельного React-приложения.

Рекомендуемый фронтенд:

- HTML-шаблоны Jinja2
- HTMX для частичных обновлений интерфейса
- Alpine.js для локального интерактива
- CSS без тяжёлого UI-фреймворка либо лёгкий Tailwind CDN/собранный CSS, если Codex сочтёт это удобным
- vanilla JS для polling статуса генерации, копирования текста и скачивания

Причина выбора: приложение должно разворачиваться на VPS через `venv`, без Docker и без сложного frontend build pipeline.

## 4. Главный архитектурный принцип

Система должна быть монолитным веб-приложением:

```text
Browser
  ↓ HTTP
FastAPI application
  ├── HTML/Jinja2/HTMX UI
  ├── Auth/session layer
  ├── Chat and article services
  ├── Prompt builder
  ├── Generation job manager
  ├── Model adapter
  ├── Admin panel
  └── SQLite database
          ↓
OpenAI-compatible vLLM API / Qwen model
```

Не нужно делать отдельные микросервисы, отдельный React frontend, Celery, Redis, Docker Compose или внешнюю очередь в первой версии.

## 6. Слои приложения

### 6.1. Presentation layer

Отвечает за:

- HTML-интерфейс;
- формы входа;
- список диалогов;
- экран чата;
- панель параметров генерации;
- админку;
- отображение сообщений;
- состояния генерации;
- ошибки;
- кнопки копирования и скачивания TXT.

Фронтенд должен быть mobile-first.

### 6.2. Router layer

FastAPI routers принимают HTTP-запросы и вызывают сервисы.

Роутеры не должны содержать сложную бизнес-логику. Их задача:

- проверить авторизацию;
- проверить права доступа;
- принять форму или JSON;
- вызвать нужный сервис;
- вернуть HTML, redirect или JSON-status.

### 6.3. Service layer

Сервисы реализуют бизнес-логику:

- создание диалога;
- проверка лимитов;
- извлечение текста из `.docx`;
- сборка промпта;
- создание generation job;
- вызов модели;
- сохранение ответа;
- создание версии статьи;
- экспорт в TXT;
- администрирование пользователей и настроек.

### 6.4. Data access layer

SQLAlchemy-модели и сессии SQLite.

На уровне моделей должны быть описаны:

- пользователи;
- диалоги;
- сообщения;
- версии статей;
- задачи генерации;
- настройки приложения;
- технические логи генерации.

### 6.5. Model adapter layer

Отдельный слой для работы с LLM.

Он должен скрывать детали OpenAI-compatible API от остального приложения.

Приложение не должно напрямую вызывать `OpenAI(...)` из роутеров или UI-слоя. Все обращения к модели должны идти через `services/model_client.py`.

## 7. Подключение модели

Модель доступна через OpenAI-compatible API.

Минимальная логика подключения:

```python
from openai import OpenAI

client = OpenAI(
    base_url=settings.LLM_BASE_URL,
    api_key=settings.LLM_API_KEY,
)

response = client.chat.completions.create(
    model=settings.LLM_MODEL_NAME,
    messages=messages,
    max_tokens=settings.LLM_MAX_TOKENS,
    temperature=settings.LLM_TEMPERATURE,
    top_p=settings.LLM_TOP_P,
)
```

На текущий момент известный пример модели:

```text
Qwen/Qwen3-32B
```

Но имя модели должно задаваться через `.env` или админскую настройку/конфиг, потому что пользователь может уточнить его позже.

### 7.1. Обязательные переменные окружения

```env
APP_ENV=production
SECRET_KEY=change-me
DATABASE_URL=sqlite:///./data/app.db

LLM_BASE_URL=https://ai.example.com/v1
LLM_API_KEY=sk-...
LLM_MODEL_NAME=Qwen/Qwen3-32B
LLM_MAX_TOKENS=2500
LLM_TEMPERATURE=0.2
LLM_TOP_P=0.8
LLM_TIMEOUT_SECONDS=180

MAX_INPUT_CHARS_DEFAULT=5000
MAX_CONCURRENT_GENERATIONS=2
```

### 7.2. Температура модели

Пользователь не должен видеть настройки температуры и top_p.

Рекомендуемые значения для новостного редактора:

```text
temperature: 0.2–0.4
top_p: 0.8
```

Причина: модель не должна фантазировать, должна строго работать с исходным материалом.

## 8. Работа с промптами

Промпт должен собираться динамически из:

1. Основного мастер-промта из админки.
2. Выбранного тона.
3. Выбранной композиции.
4. Целевой длины.
5. Количества абзацев.
6. Контекста, если он указан.
7. Сырого материала пользователя.
8. Последней версии статьи, если это доработка.
9. Пользовательской просьбы по доработке, если это follow-up.

### 8.1. Главный запрет

Модель должна использовать только данные пользователя.

Запрещено:

- добавлять факты, которых нет в исходном материале;
- придумывать даты;
- придумывать имена;
- придумывать должности;
- придумывать цифры;
- придумывать цитаты;
- использовать внешние знания;
- ссылаться на интернет;
- писать CTA.

Если данных недостаточно для заданной длины, модель должна написать более короткий материал и, если нужно, добавить вопросы к пользователю.

### 8.2. Формат ответа модели

Модель должна возвращать структурированный текст:

```text
# Варианты заголовков
1. ...
2. ...
3. ...

# Лид
...

# Статья
...

# Вопросы к пользователю
- ...
```

Если вопросов нет, раздел можно оставить пустым или написать: «Дополнительные вопросы не требуются».

Для MVP достаточно текстового формата. JSON-ответ от модели не обязателен, потому что локальные модели могут нестабильно соблюдать JSON.

## 9. Генерация статей

### 9.1. Старт генерации

Когда пользователь отправляет материал:

1. Backend проверяет авторизацию.
2. Проверяет наличие названия диалога.
3. Проверяет лимит исходного материала.
4. Если загружен `.docx`, извлекает текст.
5. Удаляет исходный `.docx` после обработки.
6. Сохраняет пользовательское сообщение.
7. Создаёт `generation_job` со статусом `queued`.
8. Возвращает пользователю экран/частичный HTML со статусом «ИИ думает…».
9. Background worker берёт задачу в работу.
10. После ответа модели сохраняет assistant message и article version.

### 9.2. Статусы задачи

`generation_jobs.status`:

- `queued` — задача создана и ждёт выполнения;
- `running` — задача выполняется;
- `completed` — ответ успешно получен;
- `failed` — произошла ошибка;
- `timeout` — модель не ответила за допустимое время;
- `cancelled` — статус зарезервирован на будущее.

### 9.3. Ограничение конкурентных генераций

В первой версии нельзя запускать слишком много одновременных запросов к модели.

Нужно реализовать простое ограничение:

- глобальный лимит одновременных генераций: `MAX_CONCURRENT_GENERATIONS`, например 2;
- один пользователь не может иметь больше одной активной генерации;
- если лимит занят, задача остаётся в статусе `queued`;
- UI показывает, что задача ожидает выполнения или выполняется.

Для MVP можно реализовать это через SQLite-таблицу `generation_jobs` и фоновую задачу внутри FastAPI-процесса.

Если приложение будет запущено в нескольких worker-процессах, такую очередь надо будет доработать. Для первой версии рекомендуется запускать один backend-процесс.

## 10. Polling статуса генерации

Так как streaming не нужен, интерфейс должен получать результат через polling.

Примерный сценарий:

1. Пользователь отправляет форму.
2. Backend создаёт задачу и возвращает `job_id`.
3. Фронтенд показывает состояние:

```text
ИИ думает…
```

4. JS или HTMX раз в 2–3 секунды вызывает endpoint статуса.
5. Если статус `queued` или `running`, индикатор остаётся.
6. Если статус `completed`, UI подгружает новое сообщение ассистента.
7. Если статус `failed` или `timeout`, UI показывает ошибку и кнопку «Повторить».

## 11. Диалоги и сообщения

### 11.1. Диалог

Диалог — это контейнер для работы над одной статьёй или темой.

Обязательные свойства:

- название;
- владелец;
- дата создания;
- дата последнего обновления;
- статус активности;
- последняя версия статьи.

Название диалога обязательно задаётся пользователем при создании.

### 11.2. Сообщения

Сообщения бывают:

- `user` — исходный материал или просьба о доработке;
- `assistant` — ответ модели;
- `system` — технические/служебные сообщения, если понадобятся.

Сообщения должны храниться в базе.

### 11.3. Последняя версия статьи

ИИ должен помнить только последнюю версию статьи.

В интерфейсе нужно показать подсказку:

```text
ИИ дорабатывает только последнюю версию статьи. Если вы хотите вернуть старую формулировку, используйте откат к предыдущей версии или напишите это явно.
```

## 12. Версии статей

Версии статей нужно хранить автоматически.

Новая версия создаётся:

- после первой генерации статьи;
- после каждой успешной доработки статьи;
- после отката к предыдущей версии, если Codex решит сохранять откат как новую активную версию.

В UI первой версии нужно реализовать минимум:

- хранение версий в базе;
- возможность откатиться к предыдущей версии;
- отображение текущей версии как сообщения ассистента.

Не нужно реализовывать diff между версиями.

---

## 13. Загрузка `.docx`

Пользователь может загрузить файл `.docx`.

Требования:

1. Принимать только `.docx`.
2. Проверять размер файла.
3. Извлекать текст через `python-docx`.
4. Нормализовать пробелы и переносы.
5. Проверять итоговый текст на лимит символов.
6. После извлечения удалить файл с сервера.
7. Не хранить оригинальный `.docx`.
8. Хранить только извлечённый текст как часть сообщения пользователя.

Если файл невозможно прочитать, показать понятную ошибку.

## 14. Ограничения и валидация

### 14.1. Лимит исходного материала

По умолчанию:

```text
5000 символов
```

Админ может изменить лимит в админке.

### 14.2. Пресеты длины статьи

Поддержать пресеты:

- `800–1500` символов;
- `1501–2500` символов;
- `2501–4000` символов.

Дефолт:

```text
1200–1500 символов
```

### 14.3. Количество абзацев

По умолчанию:

```text
4 абзаца
```

Если заданная длина конфликтует с количеством абзацев, длина важнее количества абзацев.

### 14.4. Недостаток фактов

Если фактов недостаточно, модель не должна растягивать текст искусственно.

Например: если пользователь просит 4000 символов, но фактов хватает только на 1000, модель должна написать около 1000 символов и задать уточняющие вопросы.

## 15. Стили и композиции

### 15.1. Тон статьи

Поддержать варианты:

- нейтрально-новостной;
- деловой;
- лёгкий журнальный;
- human interest.

Пользователь не может создавать свои стили в первой версии.

### 15.2. Композиции статьи

Поддержать варианты:

1. Перевёрнутая пирамида.
2. Хронологическая структура.
3. Факт → контекст → последствия.
4. Проблема → реакция → последствия.
5. Human interest.
6. Explainer / объясняющая структура.
7. AIDA без CTA.

Каждая композиция должна иметь короткое описание в интерфейсе.

Все композиции должны быть адаптированы под новости, без маркетинговых CTA.

## 17. Админка

Админка является частью того же FastAPI-приложения.

Разделы:

1. Dashboard.
2. Пользователи.
3. Все диалоги.
4. Настройки генерации.
5. Мастер-промт.
6. Debug-промпты.
7. Технические логи.

### 17.1. Настройки приложения

В базе должна быть таблица настроек.

Минимальные настройки:

- `max_input_chars`;
- `default_length_preset`;
- `default_paragraph_count`;
- `master_prompt`;
- `debug_prompt_enabled`;
- возможно `llm_model_name`, если Codex решит дать админу возможность менять имя модели без `.env`.

Секреты вроде `LLM_API_KEY` не должны редактироваться через UI в MVP. Их лучше хранить в `.env`.

## 18. Логирование генераций

Нужно хранить технические логи генераций.

Не нужно создавать отдельные текстовые log-файлы с полными промптами и статьями.

В базе хранить:

- id пользователя;
- id диалога;
- id задачи;
- время создания;
- время старта;
- время завершения;
- статус;
- длительность;
- длину входа в символах;
- запрошенную длину;
- количество абзацев;
- тон;
- композицию;
- endpoint/model name;
- ошибку, если была.

Полный промпт можно хранить отдельно только если включён debug-режим для админа. По умолчанию полный промпт лучше не сохранять в технический лог, чтобы не дублировать пользовательские данные.

---

## 19. Безопасность

### 19.1. Пароли

Пароли должны храниться только как хеши.

Запрещено хранить пароль в открытом виде.

### 19.2. Сессии

Нужно использовать безопасные cookie-сессии.

Для production:

- `HttpOnly`;
- `SameSite=Lax`;
- `Secure=True`, если приложение работает через HTTPS.

### 19.3. Доступ к данным

Пользователь видит только свои диалоги.

Админ видит все диалоги.

Все endpoints должны проверять права доступа на уровне backend, а не только скрывать кнопки в UI.

### 19.4. Файлы

Загруженные `.docx` не должны быть доступны по прямой публичной ссылке.

Оригинальные файлы удаляются после извлечения текста.

---

## 20. Ошибки модели

Model adapter должен обрабатывать:

- недоступность API;
- неверный API key;
- timeout;
- пустой ответ;
- ответ без `choices`;
- ошибку формата;
- HTTP 4xx/5xx;
- сетевые ошибки.

Пользователь должен видеть простое сообщение:

```text
Не удалось получить ответ от ИИ. Материал сохранён, попробуйте повторить генерацию позже.
```

Админ должен видеть техническую причину ошибки в логах.

---

## 21. Экспорт TXT

Экспорт `.txt` должен брать текущую последнюю версию статьи.

TXT должен содержать:

```text
Название диалога: ...

Варианты заголовков:
1. ...
2. ...
3. ...

Лид:
...

Статья:
...

Вопросы к пользователю:
...
```

Если вопросов нет, раздел можно не включать или написать «Нет».

---

## 22. Развёртывание

Целевая среда:

```text
Ubuntu 22.x VPS
```

Развёртывание:

- без Docker;
- через `venv`;
- FastAPI запускается через `uvicorn` или `gunicorn` + `uvicorn worker`;
- процесс управляется через `systemd`;
- внешний доступ через `nginx` reverse proxy;
- HTTPS через Let's Encrypt/Certbot.

SQLite-файл должен лежать в директории `data/`, которую удобно бэкапить.

## 26. Критерии архитектурной приёмки

Архитектура считается реализованной корректно, если:

1. Приложение запускается как единый FastAPI-проект.
2. Пользователи создаются только админом.
3. Обычный пользователь видит только свои диалоги.
4. Админ видит все диалоги всех пользователей.
5. Сырой материал ограничен лимитом из настроек.
6. `.docx` читается, текст извлекается, оригинальный файл удаляется.
7. Генерация идёт через OpenAI-compatible API.
8. Модель вызывается только через отдельный adapter/service.
9. UI показывает состояние ожидания ответа модели.
10. Таймауты и ошибки модели не ломают приложение.
11. Ответ модели сохраняется в истории диалога.
12. Последняя версия статьи используется при доработке.
13. Версии статей хранятся и позволяют откатиться назад.
14. Промпт собирается из мастер-промта и пользовательских опций.
15. Модель получает явный запрет на выдумывание фактов.
16. Админ может редактировать мастер-промт и лимиты.
17. Технические логи генераций сохраняются.
18. Проект можно развернуть на Ubuntu 22.x через `venv`.
