# Пользовательские сценарии AI-редактора статей

## 1. Назначение документа

Этот документ описывает основные пользовательские сценарии для веб-приложения AI-редактора новостных статей.

Документ предназначен для Codex и должен использоваться при реализации:

- пользовательского интерфейса;
- логики авторизации;
- создания и продолжения диалогов;
- генерации статей через локальную Qwen-модель;
- доработки уже созданных материалов;
- административной панели;
- обработки ошибок и пограничных ситуаций.

Проект реализуется как многопользовательское веб-приложение на Python. Приложение разворачивается на VPS под Ubuntu 22.x, работает через `venv`, использует FastAPI, SQLite и простой мобильный UI.

---

## 2. Роли пользователей

В системе есть две роли.

### 2.1. Обычный пользователь

Обычный пользователь может:

- войти в систему по логину и паролю;
- создать новый диалог;
- ввести сырой материал статьи вручную;
- загрузить `.docx` с исходным материалом;
- указать параметры будущей статьи;
- отправить материал в AI-модель;
- получить несколько вариантов заголовка, лид и статью;
- продолжить диалог с AI и доработать последнюю версию статьи;
- скопировать готовый материал;
- скачать готовый материал в `.txt`;
- видеть историю своих диалогов.

Обычный пользователь не может:

- самостоятельно регистрироваться;
- создавать других пользователей;
- менять мастер-промпт;
- видеть debug-промпты;
- видеть диалоги других пользователей;
- менять системные лимиты;
- менять endpoint модели или токен доступа.

### 2.2. Администратор

Администратор может:

- войти в систему по логину и паролю;
- создавать пользователей;
- блокировать и разблокировать пользователей;
- менять пароль пользователей;
- просматривать список пользователей;
- просматривать все диалоги всех пользователей с указанием владельца;
- редактировать основной мастер-промпт;
- менять лимит максимального размера исходного материала;
- менять дефолтные параметры генерации;
- просматривать debug-промпт, который был отправлен в модель;
- просматривать технические логи генерации;
- пользоваться редактором как обычный пользователь.

## 3. Общая логика входа в систему

### 3.1. Первый вход

1. Пользователь открывает сайт приложения.
2. Если пользователь не авторизован, приложение показывает экран входа.
3. На экране входа есть два поля:
   - логин;
   - пароль.
4. Пользователь вводит данные.
5. Backend проверяет логин и пароль.
6. Если данные верные и пользователь не заблокирован, открывается основной интерфейс.
7. Если данные неверные, показывается ошибка: `Неверный логин или пароль`.
8. Если пользователь заблокирован, показывается ошибка: `Учётная запись заблокирована. Обратитесь к администратору`.

### 3.2. Выход

1. Пользователь нажимает кнопку выхода.
2. Сессия завершается.
3. Пользователь возвращается на экран входа.

### 3.3. Регистрация

Самостоятельной регистрации нет.

Пользователей создаёт только администратор через админку.

## 4. Основной интерфейс пользователя

Основной интерфейс должен напоминать ChatGPT, но быть проще.

### 4.1. Главный экран

На главном экране пользователь видит:

- список своих диалогов;
- кнопку создания нового диалога;
- область текущего диалога;
- сообщения пользователя и AI;
- блок параметров генерации над полем ввода;
- поле ввода сырого материала или инструкции;
- кнопку загрузки `.docx`;
- кнопку отправки;
- индикатор состояния генерации.

### 4.2. Мобильный приоритет

Интерфейс должен быть удобен на мобильных устройствах.

Для мобильной версии:

- список диалогов можно скрывать в боковую панель;
- параметры генерации можно сворачивать;
- поле ввода должно быть крупным и удобным;
- кнопки должны быть достаточно большими для нажатия пальцем;
- текст статьи должен удобно читаться на узком экране.

## 5. Создание нового диалога

### 5.1. Базовый сценарий

1. Пользователь нажимает `Новый диалог`.
2. Приложение открывает форму создания диалога.
3. Пользователь должен указать обязательное поле `Название диалога`.
4. Пользователь может указать опциональное поле `Контекст`.
5. Пользователь вводит сырой материал статьи вручную или загружает `.docx`.
6. Пользователь выбирает параметры генерации.
7. Пользователь нажимает `Создать статью`.
8. Backend создаёт запись диалога в базе.
9. Backend создаёт первое пользовательское сообщение с исходным материалом и параметрами.
10. Backend создаёт задачу генерации.
11. Интерфейс показывает состояние `ИИ думает...` или `Материал в очереди...`.
12. После завершения генерации AI-сообщение появляется в диалоге.

### 5.2. Обязательные поля

Для создания первой статьи обязательны:

- название диалога;
- исходный материал статьи.

Если название диалога не заполнено, показывается ошибка:

`Укажите название диалога`.

Если исходный материал не заполнен и `.docx` не загружен, показывается ошибка:

`Добавьте исходный материал статьи`.

### 5.3. Опциональные поля

Опционально пользователь может указать:

- контекст;
- дополнительные инструкции;
- желаемый тон;
- композицию;
- диапазон длины;
- количество абзацев.

---

## 6. Ввод исходного материала

### 6.1. Ручной ввод

1. Пользователь вставляет сырой материал в текстовое поле.
2. Приложение считает количество символов.
3. Если материал не превышает лимит, его можно отправить.
4. Если материал превышает лимит, отправка блокируется.
5. Пользователь видит сообщение с текущим лимитом.

Пример ошибки:

`Исходный материал превышает лимит: 5 000 символов. Сократите текст или обратитесь к администратору`.

Лимит по умолчанию: `5000` символов.

Администратор может изменить лимит в админке.

### 6.2. Загрузка `.docx`

1. Пользователь нажимает кнопку загрузки файла.
2. Выбирает файл `.docx`.
3. Backend принимает файл.
4. Backend извлекает текст из `.docx`.
5. Backend проверяет размер извлечённого текста.
6. Если текст не превышает лимит, он подставляется в поле исходного материала или сохраняется как текст сообщения.
7. Исходный `.docx` удаляется с сервера после обработки.
8. Если файл не удалось прочитать, показывается ошибка.

Пример ошибки:

`Не удалось извлечь текст из файла. Проверьте, что это корректный .docx-документ`.

Если извлечённый текст превышает лимит:

`Текст из файла превышает лимит: 5 000 символов. Сократите документ и загрузите его снова`.

### 6.3. Хранение файла

Файл `.docx` не хранится на сервере после извлечения текста.

В базе сохраняется только извлечённый текст как часть пользовательского сообщения или исходного материала диалога.

## 7. Параметры генерации статьи

Параметры располагаются над полем ввода.

### 7.1. Тон статьи

Доступные варианты:

1. `Нейтрально-новостной`
2. `Деловой`
3. `Лёгкий журнальный`
4. `Human interest`

По умолчанию: `Нейтрально-новостной`.

Пользователь не может создавать собственные тоны.

### 7.2. Длина статьи

Длина задаётся в символах.

Доступные пресеты:

1. `800–1500 символов`
2. `1501–2500 символов`
3. `2501–4000 символов`

По умолчанию: `1200–1500 символов`.

Если в интерфейсе используется пресет `800–1500`, то внутри него нужно отдельно выделить дефолтную цель `1200–1500`, либо использовать отдельный дефолтный пресет `1200–1500`.

Важное правило: если фактов достаточно только для короткой статьи, AI не должен растягивать текст искусственно.

Пример:

- пользователь просит 4000 символов;
- исходных данных достаточно только на 1000 символов;
- AI должен написать примерно 1000 символов и при необходимости добавить вопросы к пользователю.

### 7.3. Количество абзацев

Пользователь указывает число абзацев.

По умолчанию: `4`.

Если возникает конфликт между длиной и количеством абзацев, длина важнее.

Пример:

- пользователь указал 4 абзаца;
- выбрал 2501–4000 символов;
- но исходных данных хватает только на 1200 символов.

В этом случае AI должен сделать компактный материал, не выдумывая факты. Количество абзацев можно нарушить, если это помогает сохранить качество и достоверность.

### 7.4. Композиция

Доступные структуры:

1. `Перевёрнутая пирамида`
2. `Хронологическая структура`
3. `Факт → контекст → последствия`
4. `Проблема → реакция → последствия`
5. `Human interest`
6. `Explainer / объясняющая структура`
7. `AIDA без CTA`

По умолчанию: `Перевёрнутая пирамида`.

В интерфейсе у каждой композиции должно быть краткое описание.

#### 7.4.1. Перевёрнутая пирамида

Главное сообщение ставится в начало. Затем идут детали, контекст, уточнения и второстепенная информация.

Подходит для большинства новостных заметок.

#### 7.4.2. Хронологическая структура

События описываются по порядку.

Подходит для историй, где важна последовательность действий или решений.

#### 7.4.3. Факт → контекст → последствия

Сначала основной факт, затем объяснение контекста, затем возможные последствия или значение события.

Подходит для деловых, общественных, финансовых и институциональных новостей.

#### 7.4.4. Проблема → реакция → последствия

Сначала формулируется проблема или конфликт, затем реакция участников, затем последствия.

Подходит для кризисных, конфликтных и репутационных сюжетов.

#### 7.4.5. Human interest

Материал строится вокруг человека, группы людей, ситуации или эмоционально понятного угла.

Важно: AI не имеет права добавлять эмоции, детали, биографии или обстоятельства, которых нет в исходном материале.

#### 7.4.6. Explainer / объясняющая структура

Текст простыми словами объясняет, что произошло, почему это важно и что известно из исходных данных.

Подходит для сложных тем.

#### 7.4.7. AIDA без CTA

Адаптированная новостная структура:

- внимание;
- интерес;
- детали;
- значимость.

Призыв к действию запрещён.

## 8. Генерация первой версии статьи

### 8.1. Обычный успешный сценарий

1. Пользователь заполняет название диалога.
2. Вставляет исходный материал.
3. При необходимости указывает контекст.
4. Выбирает тон, длину, композицию и количество абзацев.
5. Нажимает `Создать статью`.
6. Backend валидирует данные.
7. Backend собирает prompt:
   - основной мастер-промпт из админки;
   - параметры пользователя;
   - описание композиции;
   - ограничения по фактам;
   - исходный материал;
   - контекст;
   - требуемый формат ответа.
8. Backend отправляет запрос в OpenAI-compatible API локальной Qwen-модели.
9. Пока модель отвечает, frontend показывает состояние ожидания.
10. После ответа backend сохраняет AI-сообщение.
11. Backend создаёт первую версию статьи.
12. Frontend показывает результат в чате.

### 8.2. Формат ответа AI

AI должен вернуть материал в структуре:

```text
# Варианты заголовков
1. ...
2. ...
3. ...

# Лид
...

# Статья
...

# Вопросы к пользователю
- ...
```

Раздел `Вопросы к пользователю` показывается только если данных недостаточно или есть неопределённость.

Если вопросов нет, раздел можно не показывать.

### 8.3. Запрет на выдумывание фактов

AI должен использовать только данные, которые предоставил пользователь.

AI запрещено:

- добавлять новые факты;
- придумывать даты;
- придумывать имена;
- придумывать должности;
- придумывать цифры;
- придумывать цитаты;
- добавлять источники, которых нет в исходном материале;
- делать уверенные выводы, если они не следуют из исходных данных.

Если данных недостаточно, AI должен:

- написать более короткий материал;
- сформулировать осторожно;
- задать вопросы пользователю.

## 9. Состояния генерации

Генерация не потоковая. Пользователь ждёт полный ответ.

### 9.1. Возможные статусы задачи

Задача генерации может иметь статусы:

- `queued` — задача поставлена в очередь;
- `running` — задача выполняется;
- `completed` — задача успешно завершена;
- `failed` — задача завершилась ошибкой;
- `timeout` — модель не ответила за допустимое время;
- `cancelled` — задача отменена системой или пользователем, если такая функция будет добавлена позже.

### 9.2. Отображение статусов в интерфейсе

Если задача в очереди:

`Материал в очереди. Генерация начнётся автоматически.`

Если задача выполняется:

`ИИ думает...`

Если задача завершилась успешно:

результат появляется в диалоге.

Если задача завершилась ошибкой:

`Не удалось создать статью. Попробуйте ещё раз или обратитесь к администратору.`

Если истёк таймаут:

`Модель не ответила за отведённое время. Исходный материал сохранён, можно повторить генерацию.`

### 9.3. Повтор генерации

Если генерация упала или истёк таймаут:

1. Исходный материал и параметры не теряются.
2. Пользователь видит кнопку `Повторить`.
3. При повторе создаётся новая задача генерации с теми же данными.
4. Техническая ошибка сохраняется в логах.

## 10. Очередь генераций

### 10.1. Зачем нужна очередь

Система рассчитана примерно на 30 пользователей.

Локальная модель может не выдержать большое количество одновременных запросов. Поэтому генерации нужно ограничивать.

### 10.2. Правила очереди

- У одного пользователя может быть только одна активная генерация.
- Глобальный лимит одновременных генераций задаётся в конфиге.
- По умолчанию можно использовать лимит `1` или `2`.
- Если лимит занят, новая задача получает статус `queued`.
- Интерфейс должен показывать пользователю, что задача не потерялась.

### 10.3. Техническая реализация для MVP

Для MVP достаточно таблицы `generation_jobs` в SQLite и фонового обработчика в FastAPI.

Внешние очереди вроде Redis/Celery не требуются для первой версии.

## 11. Продолжение диалога и доработка статьи

### 11.1. Общий принцип

После первой генерации пользователь может писать AI в том же чате.

AI должен помнить только последнюю версию статьи.

В интерфейсе нужно показать подсказку:

`ИИ дорабатывает только последнюю версию статьи. Если вы хотите добавить новые факты, напишите их явно.`

### 11.2. Сценарий доработки

1. Пользователь открывает диалог с готовой статьёй.
2. Пользователь пишет инструкцию, например:
   - `Сделай текст короче`;
   - `Перепиши лид более живо`;
   - `Сделай тон более деловым`;
   - `Убери повторы`;
   - `Добавь больше акцента на последствия`.
3. Backend берёт последнюю версию статьи.
4. Backend берёт новую инструкцию пользователя.
5. Backend собирает prompt для редактирования.
6. Backend отправляет запрос в модель.
7. После ответа сохраняется новое AI-сообщение.
8. Создаётся новая версия статьи.
9. Новая версия показывается пользователю в чате.

### 11.3. Запрос на добавление неподтверждённых фактов

Если пользователь просит добавить факт, которого нет в исходном материале или последней версии статьи, AI не должен выдумывать.

Пример пользовательского запроса:

`Добавь, что компания стала лидером рынка`.

Если этого факта не было в исходных данных, AI должен ответить примерно так:

`Я не могу добавить утверждение о лидерстве компании без подтверждения в исходных данных. Укажите этот факт явно или добавьте источник/формулировку, которую нужно использовать.`

После этого пользователь может прислать новый факт. Тогда AI может использовать его в следующей версии.

### 11.4. Добавление новых фактов пользователем

Пользователь может добавить новые факты в чат.

Пример:

`Добавь факт: компания занимает 18% рынка по итогам 2024 года, по данным внутреннего исследования.`

В этом случае AI может использовать новый факт, потому что пользователь предоставил его явно.

## 12. Версии статьи

### 12.1. Создание версий

Каждая успешная генерация статьи создаёт новую версию.

Версии создаются:

- после первой генерации;
- после каждой успешной доработки;
- после восстановления предыдущей версии, если это реализовано как отдельное действие.

### 12.2. Что хранится в версии

Версия статьи должна хранить:

- ID диалога;
- номер версии;
- варианты заголовков;
- лид;
- текст статьи;
- вопросы к пользователю, если есть;
- дату создания;
- ID сообщения AI, которое создало эту версию.

### 12.3. Откат к предыдущей версии

В UI нужна простая кнопка:

`Откатиться к предыдущей версии`.

Поведение:

1. Пользователь нажимает кнопку.
2. Система находит предыдущую версию статьи.
3. Последняя версия становится предыдущей.
4. В чат добавляется системное сообщение или служебная отметка:
   `Восстановлена версия №N`.
5. Пользователь видит восстановленный материал.

Для MVP можно реализовать только откат на одну версию назад.

---

## 13. Копирование и скачивание результата

### 13.1. Копирование

У AI-сообщения с готовой статьёй должна быть кнопка `Копировать`.

При нажатии в буфер обмена копируется:

- выбранный или первый заголовок;
- лид;
- статья.

Варианты заголовков можно включать в копирование, если пользователь явно нажимает копирование всего AI-ответа.

Для MVP допустимо копировать весь AI-ответ целиком.

### 13.2. Скачивание `.txt`

У AI-сообщения или последней версии статьи должна быть кнопка `Скачать TXT`.

TXT-файл должен содержать:

```text
Заголовки:
1. ...
2. ...
3. ...

Лид:
...

Статья:
...
```

Имя файла можно формировать из названия диалога и даты.

Пример:

`nazvanie-dialoga_2026-06-16.txt`

---

## 14. История диалогов

### 14.1. Просмотр своих диалогов

Обычный пользователь видит список только своих диалогов.

В списке отображаются:

- название диалога;
- дата создания;
- дата последнего сообщения;
- краткий статус, если есть активная генерация.

### 14.2. Открытие диалога

1. Пользователь нажимает на диалог в списке.
2. Приложение открывает историю сообщений.
3. Если есть последняя версия статьи, она отображается в чате.
4. Пользователь может продолжить работу.

### 14.3. Переименование и удаление

В первой версии не требуется:

- переименование диалогов;
- удаление диалогов.

## 15. Сценарии администратора

## 15.1. Вход администратора

1. Администратор открывает сайт.
2. Вводит логин и пароль.
3. После входа видит пользовательский интерфейс и ссылку/кнопку `Админка`.

---

## 15.2. Создание пользователя

1. Администратор открывает раздел `Пользователи`.
2. Нажимает `Создать пользователя`.
3. Вводит логин.
4. Вводит временный пароль.
5. Выбирает роль:
   - `user`;
   - `admin`.
6. Нажимает `Создать`.
7. Система создаёт пользователя.
8. Администратор передаёт логин и пароль пользователю вручную.

Самостоятельной регистрации в системе нет.

### 15.3. Блокировка пользователя

1. Администратор открывает список пользователей.
2. Находит нужного пользователя.
3. Нажимает `Заблокировать`.
4. Пользователь больше не может войти в систему.
5. Его старые диалоги сохраняются.

### 15.4. Разблокировка пользователя

1. Администратор открывает список пользователей.
2. Находит заблокированного пользователя.
3. Нажимает `Разблокировать`.
4. Пользователь снова может войти.

### 15.5. Смена пароля пользователя

1. Администратор открывает карточку пользователя.
2. Нажимает `Сменить пароль`.
3. Вводит новый пароль.
4. Система сохраняет новый хеш пароля.
5. Старый пароль перестаёт работать.

---

## 16. Админ: просмотр диалогов

### 16.1. Список всех диалогов

Администратор видит все диалоги всех пользователей.

В списке отображаются:

- название диалога;
- владелец диалога;
- дата создания;
- дата последней активности;
- количество сообщений;
- количество версий статьи.

### 16.2. Открытие чужого диалога

1. Администратор открывает список диалогов.
2. Выбирает диалог.
3. Видит историю сообщений.
4. Видит последнюю версию статьи.
5. Видит debug-информацию, если включён debug-режим.

Администратор не должен случайно писать в диалог от имени пользователя.

Для MVP лучше сделать просмотр чужих диалогов read-only.

---

## 17. Админ: мастер-промпт и настройки

### 17.1. Редактирование мастер-промпта

1. Администратор открывает раздел `Промпты`.
2. Видит текущий основной мастер-промпт.
3. Редактирует текст.
4. Сохраняет изменения.
5. Новые генерации используют обновлённый мастер-промпт.
6. Старые генерации не пересчитываются.

Мастер-промпт не показывается обычным пользователям.

### 17.2. Настройки генерации

Администратор может менять:

- максимальный размер исходного материала;
- дефолтный диапазон длины статьи;
- дефолтное количество абзацев;
- таймаут генерации;
- лимит одновременных генераций;
- включение/выключение debug-режима.

### 17.3. Debug-промпт

Если debug-режим включён, администратор может видеть полный prompt, который был отправлен в модель.

Обычные пользователи не видят debug-промпт.

---

## 18. Админ: технические логи

### 18.1. Что хранить

В технических логах генерации нужно хранить:

- ID пользователя;
- ID диалога;
- ID задачи генерации;
- дату и время запуска;
- дату и время завершения;
- статус;
- длительность генерации;
- количество символов входного материала;
- выбранный диапазон длины;
- выбранный тон;
- выбранную композицию;
- количество абзацев;
- endpoint модели;
- название модели, если известно;
- HTTP-статус ответа модели;
- текст ошибки, если была ошибка.

### 18.2. Что не обязательно хранить в технических логах

Полный исходный материал и полный ответ модели не нужно дублировать в технических логах, потому что они уже хранятся в сообщениях и версиях статьи.

## 19. Ошибки и пограничные ситуации

### 19.1. Пользователь не заполнил название диалога

Ошибка:

`Укажите название диалога`.

### 19.2. Пользователь не добавил материал

Ошибка:

`Добавьте исходный материал статьи`.

### 19.3. Материал превышает лимит

Ошибка:

`Исходный материал превышает лимит. Сократите текст или обратитесь к администратору`.

### 19.4. `.docx` не читается

Ошибка:

`Не удалось извлечь текст из файла. Проверьте, что это корректный .docx-документ`.

### 19.5. Модель недоступна

Ошибка:

`AI-модель временно недоступна. Попробуйте позже или обратитесь к администратору`.

### 19.6. Истёк таймаут

Ошибка:

`Модель не ответила за отведённое время. Исходный материал сохранён, можно повторить генерацию`.

### 19.7. Пользователь уже запустил генерацию

Ошибка или предупреждение:

`У вас уже есть активная генерация. Дождитесь завершения или повторите позже`.

### 19.8. Недостаточно данных для запрошенной длины

Это не техническая ошибка.

AI должен вернуть короткий материал и вопросы.

Пример ответа:

```text
# Вопросы к пользователю
- Уточните дату события.
- Укажите должность спикера.
- Есть ли подтверждённые цифры по объёму инвестиций?
```

## 20. Минимальные критерии приёмки пользовательских сценариев

### 20.1. Авторизация

- Пользователь может войти по логину и паролю.
- Заблокированный пользователь не может войти.
- Обычный пользователь не может открыть админку.
- Администратор может открыть админку.

### 20.2. Пользователи

- Админ может создать пользователя.
- Админ может сменить пароль пользователя.
- Админ может заблокировать и разблокировать пользователя.

### 20.3. Диалоги

- Пользователь может создать диалог с обязательным названием.
- Пользователь видит только свои диалоги.
- Админ видит все диалоги с указанием владельцев.

### 20.4. Генерация

- Пользователь может отправить текст вручную.
- Пользователь может загрузить `.docx`.
- Система проверяет лимит символов.
- Система показывает состояние ожидания.
- Система сохраняет ответ AI в истории.
- Система создаёт версию статьи.

### 20.5. Доработка

- Пользователь может продолжить диалог после первой генерации.
- AI дорабатывает последнюю версию статьи.
- Новая версия сохраняется.
- Пользователь может откатиться к предыдущей версии.

### 20.6. Экспорт

- Пользователь может скопировать результат.
- Пользователь может скачать результат в `.txt`.

### 20.7. Админка

- Админ может менять мастер-промпт.
- Админ может менять лимит исходного материала.
- Админ может видеть debug-промпт.
- Админ может видеть технические логи генераций.

---

## 21. Не входит в первую версию

В первую версию не входят:

- самостоятельная регистрация пользователей;
- email-подтверждение;
- восстановление пароля по email;
- экспорт в `.docx`;
- интеграция с CMS;
- внешний фактчекинг;
- поиск по интернету;
- удаление диалогов;
- переименование диалогов;
- полноценный rich-text редактор;
- подсветка изменений между версиями;
- тонкая настройка температуры модели пользователем;
- создание пользовательских стилей;
- мультиязычность;
- отдельный React frontend;
- Docker Compose.

---

## 22. Главный принцип поведения AI

Главный принцип системы:

AI-редактор помогает превратить предоставленные пользователем факты в новостной материал, но не является источником новых фактов.

Если данных не хватает, AI должен:

- не выдумывать;
- не растягивать текст искусственно;
- писать короче;
- формулировать осторожно;
- задавать вопросы пользователю.
