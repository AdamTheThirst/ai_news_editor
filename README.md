# AI Article Editor

Многопользовательский веб-редактор новостных статей на базе локально развёрнутой LLM-модели Qwen через OpenAI-compatible API.

Проект предназначен для PR-специалистов, редакторов и авторов, которым нужно быстро превращать сырой материал, набор фактов или текст из `.docx` в готовую новостную статью на русском языке.

Главный принцип системы: **модель не имеет права выдумывать факты**. Она может использовать только те данные, которые предоставил пользователь в исходном материале и опциональном поле контекста.

---

## 1. Назначение проекта

Пользователь создаёт диалог, вставляет сырой материал статьи или загружает `.docx`, выбирает параметры будущего текста и отправляет задачу в ИИ.

Система собирает мастер-промпт из:

- основного промпта, заданного администратором;
- выбранного стиля/тона;
- выбранной композиционной структуры;
- желаемой длины;
- количества абзацев;
- исходного материала пользователя;
- дополнительного контекста, если он был указан.

После обработки модель возвращает:

- несколько вариантов заголовка;
- лид;
- готовую статью;
- вопросы к пользователю, если данных недостаточно для уверенной полноценной статьи.

После первой генерации пользователь может продолжать общаться с ИИ в том же диалоге и дорабатывать последнюю версию материала.

---

## 2. Основные требования

### 2.1 Пользователи и доступ

Приложение многопользовательское.

Регистрация самостоятельная не предусмотрена. Пользователей создаёт администратор.

Авторизация простая:

- логин;
- пароль.

Email, подтверждение почты, восстановление через email и внешние OAuth-провайдеры не нужны.

Роли:

- `user` — обычный пользователь;
- `admin` — администратор системы.

Обычный пользователь видит только свои диалоги.

Администратор видит:

- всех пользователей;
- все диалоги с указанием владельца;
- настройки системы;
- мастер-промпт;
- debug-представление полного промпта;
- технические логи генераций.

---

### 2.2 Интерфейс

Интерфейс должен быть похож на ChatGPT, но адаптирован под задачу редактора статей.

Приоритет — мобильный UI.

Общий вид:

- центральная область чата;
- список диалогов;
- поле ввода материала;
- панель параметров над полем ввода;
- кнопка отправки;
- состояние ожидания, пока модель генерирует ответ.

Переименование и удаление чатов в первой версии не требуются.

Каждый диалог создаётся с обязательным названием.

---

### 2.3 Ввод данных

Пользователь может передать исходный материал двумя способами:

1. Вставить текст вручную.
2. Загрузить файл `.docx`.

После загрузки `.docx` приложение должно извлечь текст, проверить лимит символов и удалить исходный файл с сервера. Хранить сам файл не нужно.

Материал вводится одним блоком. Отдельные поля для фактов, цитат, бэкграунда и запрещённых формулировок не нужны.

Дополнительно есть опциональное поле `Контекст`.

Контекст может использоваться для пояснения ситуации, но модель всё равно не должна добавлять факты, которых нет в исходном материале или контексте.

---

## 3. Параметры генерации

Панель параметров находится над полем ввода.

Параметры:

1. Стиль/тон.
2. Желаемая длина.
3. Композиционная структура.
4. Количество абзацев.
5. Дополнительные инструкции.
6. Кнопка сброса настроек к значениям по умолчанию.

Язык интерфейса и генерации — русский. Отдельный выбор языка не нужен.

Настройки пользователя между сессиями сохранять не нужно.

---

### 3.1 Стили и тоны

В первой версии доступны стили:

- нейтрально-новостной;
- деловой;
- лёгкий журнальный;
- human interest.

Пользовательские стили создавать не нужно.

---

### 3.2 Длина

Длина задаётся в символах.

Пресеты:

- `800–1500`;
- `1501–2500`;
- `2501–4000`.

Длина по умолчанию: `1200–1500` символов.

Если пользователь просит текст на 4000 символов, но исходных данных хватает только на 1000 символов, модель должна написать примерно 1000 символов и не растягивать материал за счёт выдумок, воды или неподтверждённых деталей.

Длина важнее количества абзацев.

---

### 3.3 Количество абзацев

Количество абзацев задаётся числом.

Значение по умолчанию: `4`.

Если требования к длине и количеству абзацев конфликтуют, приоритет имеет длина и фактическая достаточность исходного материала.

---

### 3.4 Композиционные структуры

В первой версии должны быть доступны структуры:

1. **Перевёрнутая пирамида**  
   Главное в начале, затем детали, контекст и второстепенная информация. Используется по умолчанию.

2. **Хронологическая структура**  
   События излагаются по порядку: что было сначала, что произошло потом, к чему это привело.

3. **Факт → контекст → последствия**  
   Сначала основной факт, затем объяснение фона, затем значение или последствия события.

4. **Проблема → реакция → последствия**  
   Подходит для кризисных, конфликтных и общественно значимых инфоповодов.

5. **Human interest**  
   Материал строится через человеческий фокус, ситуацию, участника или социальное значение, но без выдумывания деталей.

6. **Explainer / объясняющая структура**  
   Подходит для материалов, где важно объяснить, что произошло, почему это важно и как это понимать.

7. **AIDA без CTA**  
   Адаптированная новостная структура: внимание → интерес → детали → значимость. Призывы к действию запрещены.

В интерфейсе рядом с каждой структурой нужно показать короткое описание.

---

## 4. Правила генерации

Модель обязана:

- использовать только предоставленные пользователем данные;
- использовать все значимые факты из исходного материала;
- не добавлять неподтверждённые факты;
- не придумывать даты, имена, должности, цифры, цитаты и причинно-следственные связи;
- не имитировать фактчекинг;
- не обращаться к интернету;
- не добавлять CTA;
- не превращать новостную статью в рекламный текст;
- задавать вопросы, если данных недостаточно;
- осторожно формулировать спорные или неполные утверждения.

Если пользователь в чате просит добавить факт, которого нет в исходнике, модель должна отказаться добавлять его как утверждение и попросить пользователя предоставить этот факт явно.

---

## 5. Формат ответа модели

Ответ модели должен быть структурированным.

Рекомендуемый формат:

```markdown
## Варианты заголовков

1. ...
2. ...
3. ...

## Лид

...

## Статья

...

## Вопросы для уточнения

1. ...
2. ...
```

Блок `Вопросы для уточнения` добавляется только при необходимости.

Если данных достаточно, вопросы не нужны.

---

## 6. Доработка статьи через чат

После генерации пользователь может отправлять дополнительные команды:

- сделать короче;
- сделать подробнее;
- изменить тон;
- переписать лид;
- предложить другие заголовки;
- перестроить статью по другой композиции;
- упростить язык;
- сделать текст более деловым;
- убрать повторы;
- адаптировать под конкретный формат.

ИИ должен помнить только последнюю версию статьи.

В интерфейсе нужно показать пользователю подсказку:

> ИИ дорабатывает последнюю версию статьи. Если хотите добавить новые факты, явно укажите их в сообщении.

Каждая новая доработка создаёт новую версию статьи.

Нужно хранить версии автоматически и предусмотреть простую возможность отката к предыдущей версии.

---

## 7. История и хранение данных

Используется SQLite.

Хранить нужно:

- пользователей;
- роли пользователей;
- диалоги;
- сообщения;
- версии статей;
- настройки системы;
- задачи генерации;
- технические логи запросов к модели.

Обычный пользователь видит только свои диалоги.

Администратор видит все диалоги всех пользователей.

Исходные `.docx`-файлы после извлечения текста удаляются.

---

## 8. Технические логи

Нужно хранить технические логи генераций.

Логи должны помогать понять, почему модель не ответила или работала слишком долго.

Минимальный набор полей:

- ID пользователя;
- ID диалога;
- ID задачи генерации;
- время старта;
- время завершения;
- статус;
- размер входного материала в символах;
- запрошенный диапазон длины;
- выбранный стиль;
- выбранная композиция;
- длительность запроса к модели;
- HTTP-статус ответа модели;
- текст ошибки, если она была.

Полные тексты пользовательских материалов отдельно в технические логи дублировать не нужно, потому что они уже есть в сообщениях и версиях статьи.

---

## 9. Админка

Админка должна позволять:

- создавать пользователей;
- менять пароли пользователей;
- блокировать и разблокировать пользователей;
- видеть список пользователей;
- видеть все диалоги с указанием пользователя;
- редактировать основной мастер-промпт;
- менять лимит входного материала;
- менять дефолтный диапазон длины;
- смотреть debug-версию полного промпта;
- смотреть технические логи генераций.

Пользователь не должен видеть мастер-промпт.

Debug-представление полного промпта доступно только администратору.

---

## 10. Подключение модели

Модель подключается через OpenAI-compatible API.

Используется клиент `openai`.

Минимальный пример подключения:

```python
from openai import OpenAI

client = OpenAI(
    base_url="https://ai...",  # URL vLLM-сервера
    api_key="sk-...",
)

chat_response = client.chat.completions.create(
    model="Qwen/Qwen3-32B",
    messages=[
        {"role": "system", "content": "Вы — опытный редактор новостных статей."},
        {"role": "user", "content": "Сырой материал статьи..."},
    ],
    max_tokens=200,
    temperature=0.7,
    top_p=0.8,
)

print(chat_response.choices[0].message.content)
```

Фактические значения `base_url`, `api_key` и `model` должны задаваться через переменные окружения.

Название модели на текущем этапе:

```text
Qwen/Qwen3-32B
```

При необходимости его можно заменить позже через `.env`.

В репозиторий можно добавить только `.env.example`.

## 12. Очередь генераций

Так как приложением могут пользоваться до 30 человек, нужно защитить модель от одновременной перегрузки.

Требования:

- один пользователь не может запустить несколько генераций одновременно;
- глобальный лимит одновременных генераций задаётся настройкой;
- если лимит достигнут, задача получает статус `queued`;
- интерфейс показывает состояние ожидания;
- пользователь видит, что ИИ думает или задача находится в очереди;
- при ошибке пользователь может повторить генерацию.

Для MVP допустимо реализовать очередь через таблицу `generation_jobs` в SQLite и background worker внутри приложения.

---

## 13. Ошибки модели и таймауты

Если модель долго не отвечает:

- запрос должен завершиться по таймауту;
- пользователь должен увидеть понятное сообщение;
- исходный материал и параметры не должны потеряться;
- должна быть кнопка повторной попытки;
- ошибка должна попасть в технический лог.

Рекомендуемый таймаут: `120–180` секунд.

Если модель вернула некорректный или пустой ответ:

- нужно сохранить ошибку в лог;
- показать пользователю понятное сообщение;
- не создавать новую версию статьи из пустого ответа.

## 15. Безопасность

Минимальные требования:

- пароли хранить только в виде хеша;
- использовать безопасные cookie-сессии;
- разграничивать доступ по ролям;
- обычный пользователь не должен иметь доступ к чужим диалогам;
- админка доступна только роли `admin`;
- загруженные `.docx` не должны быть публично доступны;
- после извлечения текста `.docx` удаляется;
- секреты модели хранятся только в переменных окружения;
- debug-промпты доступны только администратору.

## 16. Рекомендуемый стек

Проект должен быть максимально простым для развёртывания на VPS через `venv`, без Docker.

Рекомендуемый стек:

- Python 3.11+;
- FastAPI;
- Uvicorn;
- SQLite;
- SQLAlchemy;

## 22. Критерии готовности MVP

MVP считается готовым, если:

- админ может создать пользователя;
- пользователь может войти по логину и паролю;
- пользователь может создать диалог с обязательным названием;
- пользователь может вставить сырой материал;
- пользователь может выбрать стиль, длину, композицию и количество абзацев;
- приложение отправляет запрос в Qwen через OpenAI-compatible API;
- пользователь видит состояние ожидания;
- модель возвращает заголовки, лид и статью;
- ответ сохраняется в истории диалога;
- пользователь может попросить доработать последнюю версию статьи;
- версия статьи сохраняется;
- пользователь может скопировать материал;
- пользователь может скачать `.txt`;
- админ может видеть все диалоги;
- админ может редактировать мастер-промпт;
- технические ошибки модели логируются;
- приложение разворачивается на Ubuntu 22.x через `venv`.
